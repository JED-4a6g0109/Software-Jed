你的專案在慢性發炎

最近在回顧至今的職涯工作碰過了不少專案，大多數的內容都在做開發>測試>佈署這流程，有些專案會因為一些原因導致時間的迭代風險越來越高，就像慢性發炎一樣在早期症狀不明顯，但到了細胞突變成癌細胞需要手術時為時已晚，或者需要投入更大的成本來治療，此篇文章將探討與分享我經歷的專案有哪些是慢性發炎症狀。以下七個症狀不分先後順序，也不一定會依序發生，任何一項單獨出現，都值得停下來檢視。

估時

當PM有新的需求或者業務邏輯改動時，工程師需要給出Effort，當你發現你的估時越大時就是一種警訊，估時這樣講有點抽象，最簡單的判斷方式就是你之前寫的程式只需1天，如今現在新增新功能或者改動你需要花費大量時間，如2~5天之類的，下面舉個例子

例子：新增一個欄位
假設 PM 提了一個需求：「使用者資料要多加一個生日欄位，前端要能填寫、後端要能存，還要顯示在會員頁面上。」
專案剛啟動的第一年，這種需求大多數人會估 0.5 天，不外乎內容為:

  • DB Migration 加欄位
  • API 加個參數
  • 前端補一個 input
  • 寫個單元測試

但是現在專案跑了兩三年後，同樣性質的需求，你發現自己估到了 3 天，而且心裡還有點沒把握。為什麼呢？ 或許你擔憂這些問題:

  • DB Migration 要小心，因為這張表已經被 5 個微服務直接讀寫，怕改壞
  • 此功能散落在多個微服務，沒有鏈路追蹤可追查
  • 這個欄位牽涉到程式碼寫的上帝物件（God Object），改一個地方要順便確認十幾個地方有沒有依賴
  • 沒有測試覆蓋，所以你得手動回歸測試整個會員模組，因為不確定會不會炸到別的功能
  • 前端那支表單元件已經被複製貼上到三個地方，你得三個都改，還要祈禱它們邏輯一致
  • Code Review 要等，因為沒人敢一個人 Merge 這種「看起來簡單但誰知道會炸什麼」的 PR

同一件事，同樣的複雜度，估時卻從 0.5 天變成 3 天以上，中間 5、6 倍的差距，這種情境發生就要注意瓶頸在哪了。

單元測試情境過少或消失

測試是很重要的，就像你吃的食物要經過檢驗、車子的引擎要經過反覆測試才能上路、醫院開給你的藥要經過層層臨床試驗，這些都是攸關安全的東西，軟體沒道理不寫單元測試。

而專案會因時間成長，效益是很可觀的，單元測試的Test Case會給你信心和節省時間。不能只依靠 QA 把關，因為 RD 自己才最熟悉程式碼的邏輯與情境。並且測試還能了解程式碼的情境和用意，有些時候Spec文件沒有更新無從得知邏輯，因此看程式碼就是最精準的解法。

如果一個專案的 Test Case 越來越少，甚至開始不寫，那就要注意了。我處理過微服務架構的系統，因為舊的專案沒有寫單元測試，導致在追溯問題時花很大量時間，最後發現底層核心系統的Enum少加了一個Key，且function也沒寫最基礎單元測試。事後回頭看，當初補一個測試案例只需要五分鐘，而這次代價卻是兩個工程師耗了一個下午，這就是不寫測試真正的成本，它不會馬上發生，一旦發生時間成本比你開發還要多倍。

假覆蓋率

覆蓋率指的是單元測試所測的所有專案範圍，有些主管或者公司會擬定專案要滿足幾%的覆蓋率才能佈署，我先說這是好的至少可以保證你有寫測試覆蓋到那些模組或核心業務避免遺漏，但往往覆蓋率指標設為太高就不是好事了，例如將覆蓋率門檻設在85-100%這種標準，我認為不是每個專案都能達成的，而那些專案沒辦法達成就會用一些奇怪的手段來騙過覆蓋率檢查機制

  • Happy Path（快樂路徑）
    簡單來說，單元測試只寫是最順利、完全沒出錯的理想狀況。測下來一路PASS，測試工程師與開發工程師還有PM都很Happy，也能增加覆蓋率。
  • 假單元測試
    覆蓋率過高有些工程師就會開始偷懶，在單元測試裡面寫假單元測試，而實際是在做整合測試將覆蓋率數字衝高，但這違反了單元測試初衷，還遺留了垃圾code在裡面，因為這種測試毫無價值可言，下面舉個程式碼例子

計算消費稅與下單功能

工程師的單元測試只針對 create_order(a)寫，因為「反正跑起來會過，覆蓋率也會漲」

問題在於粒度錯了，兩者職責不同，理應各自獨立測試。

  • Ignore註解大法
    有些工具有提供Ignore功能來避免計算進覆蓋率，如pytest # pragma: no cover，工程師不知道怎麼寫或是偷懶就會用此招，覆蓋率報告因此顯示 95%，但真正沒被驗證的，恰好是最容易出錯、最該被保護的分支邏輯
  • 測試無關緊要的東西
    覆蓋率不夠就會開始寫一些垃圾單元測試，例如測試第三方function、framework方法、甚至連DTO一些無邏輯程式碼

這些手法的共同點是，數字很誠實地反映了「你寫了測試」，卻完全不反映「系統被驗證過」，覆蓋率報告變成一份好看的謊言。

明確的危險症狀

幾乎每個做過專案的人都聽過這句話：「這邊別動，能跑就好」。團隊心裡都清楚哪裡是雷區，某段邏輯沒人懂當初為什麼這樣寫、某個模組改一行就牽動十個地方。這不是沒人發現問題，恰恰相反，大家都知道，只是選擇繞過去。

繞過去的理由永遠一堆:

  • 時程太趕
  • 政治敏感
  • 跨部門溝通成本太高
  • 耦合度太深動不了
  • 業務邏輯太重不敢碰

業務需求會變、依賴套件會爆出資安漏洞、雲端服務商會停止支援舊版本，外部世界不會等一個程式碼庫自己想通再變動。沒有一個專案能永遠不更新、不佈署，遲早有一天，那個「別碰的地方」會被迫碰。

當出現不得已要開始改動時，已經太晚了，通常主管通常會開始評估兩條路：

  • 局部重構
  • 另開新專案做 Migration

但要提醒的是，Migration 從來不是必然選項，只是當耦合深到連局部重構都無法切入時，才會被迫走這條成本最高、風險最大的路。多數情況下，漸進式重構才是更務實的第一選擇。

手動

人都會犯錯，沒有人是完美的。就算你自己夠仔細不會出錯，也要考慮到同事，以及未來接手的同仁未必知道你動過什麼。

我自己就遇過一次教訓：曾經為了協助 QA 建立測試環境，手動改動了程式碼內部的參數，事後忘記調整回去，發 PR 時同事也沒注意到，最後這段改動被佈署上線，導致產品故障。而所有系統任何地方都不應該出現手動，如果出現請警惕並分析為啥還不調整自動，而系統任何的手動會衍生出三個問題：

  • 沒有 Audit Trail：出事時完全查不到是誰動的、什麼時候動的，究責無從查起
  • 無法維護：沒人知道系統實際被改成什麼樣子，接手的人像在拆一顆不知道線路的炸彈
  • 增加犯錯風險：手動操作本身就比自動化更容易出錯，而且每次都要重新花時間確認

如果你的專案裡還存在這種手動操作，就跟身體裡的腫瘤一樣，現在看起來沒事，只是還沒等到它癌變的那一天。

拒絕當算命師

在開發時，很多時候明明需求還不明確就開始過度設計，或預先開發，但我認為這是無意義且增加技術債的行為。我自己的判斷標準是

只要這個需求還沒被放進 Backlog、PM 也沒有明確拍板未來一定會做，只是目前先擱置，我一律不會因此改變我的設計或預留彈性。

原因是業務需求本來就是多變的，你今天猜的「未來可能會這樣用」，很可能三個月後方向完全變了，甚至這個需求根本被砍掉。你現在為了「可能發生的未來」多寫的抽象層、多留的參數、多繞的彈性設計，只會換來一個結果

系統複雜度變高，而複雜度是不會自己消失的，它會一直留在那裡，變成往後每個人都要多花時間理解的成本。

有些人會反駁:「程式碼寫得有彈性、好擴展、好維護，這不是好事嗎？」這句話本身沒有錯，我也不否認彈性設計、可維護性是好的工程實踐，但這跟「為一個還不存在的需求預先設計」是兩碼子事。彈性應該是為了「已知會變動的東西」而準備，不是為了「你猜測會發生的東西」而準備。

既然需求還沒確定，為什麼不等它明確下來再開發？你現在腦中預想的方案，真的能保證就是未來需求出現時的最佳解嗎？多數時候答案是不能，你今天猜的彈性設計方向，未來需求真的來的時候，往往剛好不是那個方向，於是你多留的彈性完全沒用上，反而變成一段增加理解成本、卻從未被使用過的死程式碼。與其賭一個不確定的未來，不如把力氣留到需求真正確定的那一刻，用當下最清楚的資訊做出最合適的設計。

佈署恐慌

佈署頻率持續下降，是需要提高警覺的訊號。任何有價值的系統都不會出現這種現象，就算是穩定成熟的系統，也會有例行的優化與維護性更新，佈署次數不會無緣無故越來越少。

當專案惡化到沒人敢佈署、連一個小功能上線都要提心吊膽、每次佈署 Product 都會炸，基本上已經是末期病徵，通常代表 Migration 已經是唯一選項了。不過這裡要區分兩種佈署頻率下降的成因：

一種是系統本身太脆弱、變更成本太高（前面講的情況），另一種其實是團隊士氣低落或人力流失導致產出變慢，跟程式碼健康度無關。這兩者外在症狀很像，但病因完全不同，不要把士氣問題誤診成技術債，反過來也不要把技術債問題誤診成人的問題。

結論

文內所提的

  • 估時暴增
  • 測試消失
  • 覆蓋率造假
  • 危險地區浮現
  • 手動操作蔓延
  • 預先為未來過度設計
  • 佈署頻率下降

這七個症狀很少同時出現在同一天，它們是慢性的、漸進的，就像發炎初期你甚至不會特別在意。但等到多個症狀同時出現、團隊已經對佈署感到恐慌時，通常代表病灶已經不是吃藥調理能解決的範圍了，而是要動刀，也就是前面提到的重構或 Migration。

慢性發炎最麻煩的地方就是你對於這些小問題不會有太大感覺，你覺得只是小感冒或者身體痠痛過幾天就好，但是沒有人能準確預測「還剩多少時間」，等到症狀越來越明顯基本上就罹癌了，與其等到不得不動刀那天，不如現在就開始留意這些訊號，越早發現，治療成本越低。
