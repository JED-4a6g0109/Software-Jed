從Concurrency與Parallelism概念去了解Python: Multiprocessing、Threading、Coroutine、asyncio

最近工作上用了Concurrency，在跟同事解釋發現對方能理解Parallelism，但卻不太明白Concurrency，我後來想了一下應該要寫一篇文章搭配圖文解釋這兩者差異，並介紹一下在Python GIL限制下如何解決？又或者如何最佳化運用CPU。

併發(Concurrency)

定義：讓多個任務在「重疊的時間範圍」內進行，但不一定是同時執行。
即使只有一顆 CPU 核心，透過快速切換(context switching)，在等待過程中切換到須處理的任務，然後再回來處理，來達成併發目的。

假設你要一人完成三件家事：洗衣服、拖地、燒開水。

  • 把衣服丟進洗衣機，按下開關 → 離開
  • 把水壺裝滿放上瓦斯爐 → 離開
  • 趁著這段空檔開始拖地
  • 水燒開了 → 記下拖地拖到哪、停下 → 去關瓦斯
  • 回來繼續拖地
  • 洗衣機音樂響了 → 一樣記下位置、停下 → 去曬衣服
  • 曬完衣服 → 回來把剩下的地拖完

如果不能中途切換，你就得死盯著水壺看它燒開，其他事情完全不能做，這樣就不是併發了。「併發」的核心不是任務本身，而是能不能交錯處理。

平行(Parallelism)

定義：多個任務真正同時執行，需要多個運算單元(多核心 CPU、多台機器等)。Parallelism 是 「真的同時」，而不只是「交錯」。

延續剛剛的家事情境，這次你請了室友一起幫忙。你們一人一顆頭腦、一雙手，可以真的在同一個時間點分頭進行不同的事情：

  • 你負責洗衣服和拖地，室友負責燒開水
  • 你把衣服丟進洗衣機、按下開關，接著開始拖地
  • 與此同時，室友正站在瓦斯爐前顧著水壺，兩件事在同一秒鐘都在發生
  • 水燒開了，室友自己處理，不需要打斷你拖地的動作
  • 你們各自完成手上的工作，最後同時把家事做完

這裡的關鍵差異在於：你們兩人是各自獨立運作的個體，沒有互相等待、也不需要交錯切換你拖地的當下，室友確實正在燒水，這是物理上真實發生的「同時」，而不是像一人做家事時，靠著記錄進度、來回切換造成的「感覺上同時」。

以上你把家事情境的人想像成CPU的核心數，當一人時等同一核心，兩人為兩核心去處理事務

講述了Concurrency 與 Parallelism，接著來介紹這兩者適用在何種場景下

I/O bound、CPU bound

關於何種場景選項哪項處理那就要講到 I/O bound、CPU bound，這兩項一樣先用做家事例子來解釋

  • 洗衣服、燒開水——這些是「丟出去等結果」的事，你按下開關後人是空的，等待期間沒在耗費你的「腦力」，只是在「等」。這對應 I/O bound：程式在等網路回應、等硬碟讀寫、等資料庫查詢，CPU 其實是閒置的，很適合用 concurrency（像 asyncio、多執行緒）見縫插針去處理其他任務。

  • 拖地——這件事沒辦法丟出去等，從頭到尾都要你自己動手、持續耗費你的體力（運算資源）。這對應 CPU bound：像圖片處理、大量數值運算，過程中沒有「等待」的空檔可以切換，真正想加速只能靠「多找幾個人一起拖」（多核心、multiprocessing）。
    以上解釋完再來講講定義

CPU bound

定義：程式的執行速度受限於 CPU 的處理能力(核心與時脈)。狀態：執行時，CPU 使用率會長期處於極高狀態，而記憶體、硬碟、網路等設備大多處於閒置狀態。
場景：程式有大量的數學運算、邏輯判斷或資料轉換，幾乎不需要等待外部設備。
例子: for loop、數據運算(如影像處理)

I/O bound

定義：程式的執行速度受限於 I/O(Input/Output)設備的讀寫速度。執行時，CPU 長期處於等待狀態，使用率極低。時間都花在等待外部資料傳輸完成。
場景：程式碼本身執行得極快，但需要頻繁與硬碟、網路、資料庫或周邊設備進行資料交換。
例子: 後端服務、爬蟲

執行完時間會在1秒左右，threads 都在做 I/O bound 的事（例如 5 個 HTTP request），某個 thread 一遇到 requests.get() 這種等待網路回應的動作，就會主動讓出 GIL，換下一個 thread 上場。因為網路等待本來就是「空檔」，5 個 threads 交錯利用這些空檔，整體效率確實比循序執行快很多，所以這種I/O bound場景很適合做併發處理。

在 Python 裡，threading 幾乎等於 concurrency 的實作，而不是 parallelism，真正想要平行運算 CPU bound 任務，得靠 multiprocessing 繞過 GIL，又或者使用python 3.14以後版本目前官方正在往移除GIL限制邁進，以現在我們來直接用multiprocessing來做平行運算。

耗時會相較前者threading快很多可以自行嘗試。

上面介紹了Python threading 與multiprocessing，雖然threading受GIL鎖限制沒辦法達到平行運算，但他有併發特性在 I/O bound場景下，把等待的時間加以利用進行速度的提升，但也侷限在「有等待的時間這點上」，像我們舉的for例子就沒辦法提速了，因此才需要multiprocessing去繞過Python GIL鎖來達成真正的平行運算，因此先確定場景再進行要選擇 threading 與multiprocessing極其重要。

以上是threading 與multiprocessing的介紹，然而threading在某些場景下就不是這麼適合了

後端服務大量請求問題

像是後端服務讓Client同時連線並處理請求，後端服務大量的thread可能會導致在同時間大量請求時，每個threading要吃掉MB 級的記憶體，而且 OS 排程、切換上千個執行緒的成本很高。當連線數飆到幾千、幾萬，用執行緒硬撐會直接把伺服器拖垮。

Threading 的併發問題

OS 可以在你程式碼的任何一行之間插手切換執行緒，完全不受你控制。這帶來Race condition（競爭條件）到處都是，你必須自己判斷「這段共享資料需不需要上鎖」，一旦漏掉就是很難重現的 bug，此外除錯困難，因為每次執行的交錯順序可能都不一樣，如果跑過上面例子你就能看到Threading交錯的結果，非常不好除錯

因此在當時背景下大家為了解決這問題才出現了Coroutine

Coroutine

開了threading但是遇到除錯跟成本開銷過大，問題本質就是要解決I/O bound問題，那只在CPU 完全閒置下，記住等一下要從哪裡繼續，一閒置就開始找事情做不就好了，所以開始有了往Coroutine下手方向，Coroutine是一種可以在執行中途暫停、之後又能從暫停處恢復的函式，一般函式的執行權是「單向交出去、一次性拿回來」，而協程的執行權是「可以來回交接好幾次」。以下用堆疊的角度看，更容易懂原理

graph LR
    A["main() 呼叫 foo()"] --> B["foo() 執行"]
    B --> C["foo() 執行完畢"]
    C --> D["從 stack 上移除"]
    D --> E["回到 main()"]

foo() 執行完就徹底結束了，它的區域變數、執行到哪一行，全部都沒了。下次再呼叫 foo()，是全新的一次執行，不會記得上次跑到哪。

但Coroutine 不一樣，它有能力保留自己的執行狀態，執行到第幾行、區域變數目前的值，暫停之後，這些狀態不會被清掉，而是被凍結保存起來，等下次恢復時，直接從凍結的地方接著跑

sequenceDiagram
    participant 呼叫端
    participant Coroutine
 
    呼叫端->>Coroutine: 第一次執行
    Coroutine-->>呼叫端: 跑到一半，暫停(狀態凍結保存)
    Note over 呼叫端: 中間別人在跑別的東西
    呼叫端->>Coroutine: 恢復執行
    Coroutine-->>呼叫端: 從凍結處接著跑，跑到一半再暫停

因此Coroutine解決I/O bound問題也不用開了threading，Python又是怎麼實現這特性呢?這就要講一下asyncio

asyncio 的出現以及原理

在早期其實大家都知道這困境因此都各別實作coroutine，一直到 yield from 語法以及generator出現，Python 選擇用 generator 作為協程的底層實作基礎，因為 generator 本來就有「暫停並保留狀態」的能力

yield 是暫停鍵

send() 是繼續鍵

有了這些Python特性後來才出現了asyncio框架來實現Coroutine，而async def 定義出來的協程，骨子裡就是包了一層的 generator，靠同一套「凍結/恢復執行狀態」的機制運作，只是把 yield 換成用 await 呼叫 await() 來觸發。

asyncio 基礎認識

asyncio非常簡單且易用，需要在def 前加上async，以及調用function 時前面加await

如果調用function時，前面沒加上await，會獲得coroutine物件，必須用 await 或交給事件迴圈才會真的執行。關於啥是事件迴圈後面會講到，這邊先記得這東西就好。

await = 呼叫 await() 並把 yield 一路往外傳
await X 本質上就是呼叫 X.await()

  • 如果裡面有 yield → 暫停會一路往外傳，最終傳到最外層呼叫 send() 的地方(也就是事件迴圈)，控制權真的被交出去
  • 如果裡面沒有 yield → 直接執行完，跟呼叫一般函式沒兩樣，控制權沒有交出去

    await 可以控制，而不像threading全由OS調度，在除錯上也非常好做，解決前面所提threading遇到的尷尬問題

Event Loop

事件迴圈（Event Loop） 是 asyncio 的大腦，一切都圍繞著它運作。簡單了解白話就是指揮官，想像開大型貨輪的船長他會指派工作給所有船員做事，事件迴圈也是這道理

graph LR
    A["工作 A - 等待中"] --> EL(("事件迴圈<br/>Event Loop"))
    B["工作 B - 執行中"] --> EL
    C["工作 C - 等待中"] --> EL
    EL --> S["誰準備好就做誰"]

事件迴圈是單執行緒的。所有工作看起來「同時」進行，其實是靠不斷快速切換造成的錯覺就是前小節講的Concurrency機制，不是真的平行運算。

運用在後端服務上

前面所提問題，那要如何實作呢? 其實很簡單先來看一般同步寫法

用 asyncio

CPU 完全閒置，什麼都沒做，卻硬生生卡住 1 秒。asyncio在等待網路回應的這 1 秒 CPU 也沒事做，那不如利用這段空檔去處理其他 99 個請求

結論

整理一下這篇文章想講的核心概念：

Concurrency vs Parallelism

  • Concurrency 講的是「有沒有辦法交錯處理」，重點不在同時發生，而是在等待的空檔塞入其他工作，就算只有一顆 CPU 也能做到。
  • Parallelism 講的是「真的同時發生」，需要多個運算單元（多核心、多台機器）才能達成。
    先分辨場景，再選工具
  • I/O bound（等網路、等硬碟）：CPU 大部分時間都是閒置的，很適合用 concurrency 見縫插針去利用這些空檔，像 threading、asyncio。
  • CPU bound（大量運算）：CPU 全程滿載，沒有閒置空檔可以利用，真正要加速只能靠 parallelism，也就是 multiprocessing。
    Python 的限制與解法
    Python 有 GIL 鎖住同一時間只能有一個 thread 執行 bytecode，所以 threading 在 Python 裡本質上還是 concurrency，而不是 parallelism；CPU bound 場景下開再多 threading 也不會變快，得靠 multiprocessing 繞過 GIL 才能真正做到平行運算。

但 threading 也有自己的問題：資源開銷大、OS 排程切換成本高、還有難以除錯的 race condition。為了解決這些，才有了 coroutine 這種「主動讓出控制權」的機制，Python 用 generator 的 yield/send 實作出協程的底層基礎，再包裝出 async def / await 語法，最後由 asyncio 這個框架負責排程，透過事件迴圈在單一執行緒裡高效率地處理大量 I/O bound 任務，而不需要真的開一堆 thread 或 process。

先判斷任務是 I/O bound 還是 CPU bound，I/O bound 用 concurrency（threading / asyncio），CPU bound 用 parallelism（multiprocessing），用對工具、選對武器，才是解決問題的關鍵。
