輪詢 vs 長輪詢 vs Webhooks vs SSE

屬於客戶端-伺服器通訊模式(Client-Server Communication Patterns)設計，主要解決Client與Server用哪種設計來達成資訊的通訊，其實還有更多設計，只是這四種目前普遍大家常看到的設計，而他的優缺點bytebytego其實很精簡介紹了，但他並沒有說為何這樣設計?或者啥場景要怎樣用?以下我將以我個人經驗來補充說明。

輪詢

輪詢的本質：把同步責任從被動方轉移到主動方

如果你去看輪詢在業界的實際案例，會發現它幾乎都圍繞著同一個核心動機「解耦」。

以監控系統為例，假設你要監控 1000 台伺服器的 CPU、RAM 使用率，理論上你有兩個選擇：

  • Push 模型：每台伺服器自己主動把數據推給監控中心
  • Pull 模型（輪詢）：監控中心主動去每台伺服器抓數據

如果選 Push，代表每一台被監控的伺服器都要：

  • 知道監控中心在哪裡（URL、認證方式）
  • 自己維護「定期推送」的邏輯
  • 監控中心搬家或改設定，1000 台伺服器全部要跟著改

這就是典型的強耦合：被監控方被迫綁死監控中心的存在與細節。

而 Prometheus 選擇 Pull（輪詢）模型正是為了解決這個問題：被監控服務只需要被動暴露一個 /metrics endpoint，完全不用知道 Prometheus 是誰、在哪裡、用什麼頻率抓取。所有「什麼時候抓、抓多頻繁、失敗要不要重試」的邏輯，全部集中在 Prometheus 這一端，被監控方只需開一個API成本也不高也不難。

sequenceDiagram
    participant P as Prometheus（監控中心）
    participant S1 as Server A
    participant S2 as Server B
    participant S3 as Server C
 
    Note over P: 主導抓取節奏，自行排程
    P->>S1: GET /metrics
    S1-->>P: 回傳 CPU/RAM 數據
    P->>S2: GET /metrics
    S2-->>P: 回傳 CPU/RAM 數據
    P->>S3: GET /metrics
    S3--xP: 逾時無回應
    Note over P: 判定 up == 0（服務可能掛了）
    Note over S1,S3: 被監控方完全不知道<br/>Prometheus 是誰、在哪裡

三個條件輪詢才是最佳解

解耦本身不足以說明「輪詢是最佳方案」，如聊天室功能，輪詢在這場景反而是爛選擇。真正讓監控場景成為輪詢最佳解的，還要考量以下兩點

延遲容忍度與資料變化速度對齊
CPU、RAM 這類指標的變化本身就是秒級的，監控儀表板或設定告警規則時，決策動作本來也是分鐘級的(例如CPU 持續超過 80% 超過 1 分鐘才告警)。輪詢的延遲上限等於輪詢間隔，只要間隔(Prometheus 預設抓取間隔通常落在 15 秒左右，可依需求調整)比監控目標的變化速度更快，資訊價值幾乎不會流失。

如果你為了監控場景去上 WebSocket 換取毫秒級即時性，那是典型的過度工程「你付出了維持大量長連線的資源成本，卻沒有任何實際場景用得上這個精度。」

監控方能主導抓取節奏，換取負載可預測性
假設監控 10,000 個服務，如果是 Push 模型，這 10,000 個服務有可能因為部署時間相近，在某個時間點集中同時推送數據過來，形成 thundering herd，監控中心反而要應付不可預測的流量尖峰。而 Pull 模型讓 Prometheus 自己決定抓取排程，可以刻意分批、錯開抓取時間，把負載壓成一條平滑的曲線。

輪詢適合場景，通常需要同時滿足三個條件:

  • 存在真實的解耦需求
  • 資料變化速度與使用者的決策節奏在同一個數量級，可以容忍秒級以上延遲
  • 資料的接收方能夠主導同步節奏，以換取負載可預測性

長輪詢

短輪詢有一個結構性缺陷就是延遲上限永遠等於輪詢間隔。間隔設 3 秒，最壞情況資料要等接近 3 秒才會被看到；想降低延遲，就得縮短間隔，但這樣一來大部分請求都是沒事的空跑，浪費頻寬與伺服器運算資源。

長輪詢的做法是把「等待」這件事從客戶端搬到伺服器端，客戶端發出請求後，伺服器先掛著連線不回應，直到有新資料或逾時才回應，回應完客戶端立刻再發下一次請求。這樣一來，只要有新資料，幾乎是立即被推送出去，同時又不像短輪詢一樣大量發送空請求。

sequenceDiagram
    participant C as Client
    participant S as Server
 
    C->>S: 請求資料
    Note over S: 連線保持開啟<br/>等待新資料或逾時
    Note over S: ...資料還沒來...
    Note over S: 新資料出現！
    S-->>C: 立即回應（附帶新資料）
    C->>S: 馬上發出下一次請求
    Note over S: 連線保持開啟<br/>等待新資料或逾時
    Note over S: 逾時，無新資料
    S-->>C: 回應空結果（timeout）
    C->>S: 馬上再發出下一次請求

不過我自身工作經驗沒有看到任何長輪詢的設計，我個人覺得這設計很尷尬，如果很強求即時的話又或者想解決輪詢等待秒速，用WebSocket就好幹嘛還用長輪詢，如果可以接受延遲那我就用輪詢就好啊不必搞那麼複雜設計，因此長輪詢在技術演進史上比較像是一個過渡方案，它出現在「短輪詢延遲太高」與「WebSocket 尚未成熟或瀏覽器 / 防火牆不支援」這兩個限制中間的空隙，這種場景越來越少見（雲端原生架構普及、WebSocket 相容性問題被解決）。

Webhook

Webhook 是雙向的硬約定，也是「Push 模型」的代表。Webhook 的雙方會有一個接口，當事件完成，會透過 Webhook 方式來進行通訊，因為這個特性，所以它是強耦合的，只要其中一個接口壞掉會使功能無法正常運作。

此外，Webhook 很常運用在事件驅動場景，事件的即時性是 CI/CD 場景的核心需求，可以在 GitLab 或 GitHub 上看到有 Webhook 的設置。

Webhook 兩端至少要在三件事上死死綁定，之前工作經驗中有建立CI/CD這裡以 GitLab 為例：

  • URL：接收方的網址一改，發送方（GitLab）的設定就要跟著改，不然事件直接送不到
  • Payload 格式：GitLab push event 的 JSON schema 長什麼樣、欄位叫什麼名字，接收端的解析邏輯完全綁死這個格式，GitLab 如果哪天改了欄位命名，你的接收端解析邏輯可能直接壞掉
  • Secret Token / 簽章機制：雙方要對好同一組密鑰，任何一方換了都要同步通知另一方

這些都是實打實的契約層級耦合，但也正因為遵循同一套契約，就能與各種服務做整合一套機制可以支援無限多種下游用途，而不用為每個整合維護客製化程式碼，這是它換來的擴充性。

輪詢是消費方（Prometheus）主導節奏、可預測，也因此換來了「解耦」被監控方完全不用知道 Prometheus 的存在。Webhook 剛好相反，它是發送方（GitLab）主導節奏，接收方只能被動承接，用的是一次性但緊密的契約耦合（URL、Payload 格式、Secret Token）去換取即時性。換句話說，輪詢用「Pull」換到的是解耦，Webhook 用「Push」換到的是即時性，但代價轉移到了不同的地方

雖說webhook接口是強耦合，但以業務邏輯來說，這種「通知」與「處理」的分離，讓 GitLab 的核心系統維持單純，它只要保證事件正確發出去，不用介入下游的業務邏輯，等於讓事件通知邏輯與業務邏輯解耦。

SSE

SSE 也是「Push 模型」，由瀏覽器主動發起一條 HTTP 連線，但這條連線不像一般 HTTP 請求收到回應就結束，而是持續開著，伺服器可以在同一條連線上持續、不斷地推送新的資料片段過去。它與前面所提的輪詢剛好相反，且它與 WebSocket 很相似，只是它是單向的。

所以 SSE 佔的位置是「單向 ＋ 事件不規律 / 持續但無法預測節奏」。

sequenceDiagram
    participant B as 瀏覽器
    participant S as Server
 
    B->>S: 建立連線（EventSource）
    Note over B,S: 連線持續開啟，不會像一般 HTTP<br/>收到一次回應就結束
    S-->>B: event: token 1
    S-->>B: event: token 2
    S-->>B: event: token 3
    Note over S: 生成速度不固定<br/>資料片段不規律送達
    S-->>B: event: token N（完成）
    Note over B,S: 同一條連線持續使用<br/>直到任務結束或斷線

舉例來說，近年的 AI Chat 就很適合 SSE 場景：模型一邊生成 token，伺服器就一邊把片段推送給前端，前端收到就即時渲染，而不是等整段生成完才一次回傳。這個場景完美符合 SSE 的特性：

  • 單向：前端不需要在生成過程中插話
  • 資料是持續但不規律的片段流：生成速度不固定，沒辦法用固定間隔輪詢
  • 基礎設施相容性好：走標準 HTTP，前端設置也相對簡單容易
    如果想實作，可以參考這篇文章：OpenAI SSE (Server-Sent Events) Streaming API

所以怎麼判斷該不該用 SSE? 我的答案很簡單，使用者收到資料的同時，需不需要透過同一條連線傳點東西回去，我認為很適合SSE這場景。

結論

回頭看這四種模式，其實可以收攏成同一個決策框架，用兩個維度分類：

  • 通訊方向（單向／雙向）
  • 誰主導同步節奏（消費方 Pull／發送方 Push）。
Pull（消費方主導） Push（發送方主導）
單向 輪詢、長輪詢 Webhook（伺服器對伺服器）、SSE（對瀏覽器）
雙向 — WebSocket

輪詢跟長輪詢都是消費方主動去問，差別只在於「等待」這件事發生在客戶端還是伺服器端；Webhook 跟 SSE 都是發送方主動推送，差別在於接收方是不是一個有固定 URL 的後端服務，是的話用 Webhook，不是（例如瀏覽器）就用 SSE；而 WebSocket 則是唯一支援真正雙向溝通的選項。

以上是結合自身工作經驗和自學所補充的內容，我認為 bytebytego 那篇文章可惜的地方，它把四種模式的優缺點列得很整齊，卻沒有往下追一層「為什麼是這個場景」、「要解決甚麼?」、「設計的演變」。只有優缺點列表能幫你快速認識這四種模式的存在,但真正決定你該選哪一種的，永遠是你手上這個場景的三個條件對不對得上號。只用了一張圖告訴你基礎內容，但卻沒有一個完整例子解釋，或是更深入的探討，我還是Junior時確實能讓我快速知道有這些方式，但以senior的角度內容有點空洞。
