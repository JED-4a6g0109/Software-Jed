架構模式BFF(Backend for Frontend)是什麼?

在現在公司以及軟體規模，通常後端需要同時要支援 Web、iOS、Android 甚至第三方合作夥伴的產品,在後端 API開發上可能會遇到前端夥伴一些需求

  • 這支 API 給的資料不是我要的格式
  • 我要打三支 API 才能拼出一個畫面
  • 要客製化的前端專屬業務邏輯
  • API怎麼打?怎麼接?

而以上這正是 BFF(Backend for Frontend)這個架構模式想解決的問題。

BFF 是什麼?

SoundCloud 早在 2013 年就率先提出了後端服務前端(BFF) 架構模式， 與其讓所有前端(Web、iOS、Android、第三方)共用同一組通用後端 API，不如為「每一種前端」量身打造一層專屬的後端服務。

每個前端對應一個(或一組)專屬 BFF，BFF 再去呼叫底層各個領域的微服務，聚合、轉換之後回傳給前端。它介於「前端」與「底層核心服務(微服務、資料庫、第三方系統)」之間負責:

  • 聚合多個微服務的資料，組成前端要的單一回應
  • 針對特定裝置或平台做資料處理或格式轉換
  • 處理該前端專屬的認證、快取、錯誤處理邏輯
  • 隔離前端變動對核心服務的衝擊
    簡單說，BFF 讓「前端想要什麼形狀的資料」跟「後端實際怎麼存資料」這兩件事解耦，以及簡化前端需要學習後端API服務開怎使用的學習成本(後端服務有時API是多層的非常複雜)

BFF設計帶來什麼好處?

支援不同前端的需求差異化

  • 商業模式導致的差異
    有些是出於商業模式，又或者前端侷限而導致不同端的需求會有些微差異，例子:
    電商平台的 Web 後台(給商家用)需要完整的營收報表、庫存明細、財務數字;但消費者端的 Mobile App 只需要簡化過的商品資訊與訂單狀態，因為使用情境不同(商家在辦公室分析數據 vs. 消費者滑手機下單)。

  • 前端技術侷限造成的差異
    Mobile App 在行動網路環境下要考慮流量與電量，BFF 可以做資料的Cache，又或者大量計算可以由後端算完將結果傳至前端，來降低前端運算電力消耗問題

減少前端的API學習成本

沒有 BFF 的情況下，前端常常得自己打好幾支 API，再自己組裝資料、處理錯誤、做重試邏輯。這些邏輯搬到 BFF 之後，前端只要呼叫一支專門為它設計的 API，拿到剛剛好的資料就好，畫面邏輯乾淨很多。解決了前端開發上無需學習後端API成本

後端領域服務

  • 端與端之間解偶非強耦合在同後端服務
    核心微服務可以維持通用、穩定、不隨前端需求變動的設計，不必為了遷就某個特定前端而妥協資料結構。BFF 則是變動最頻繁、最貼近使用者體驗的那一層，兩者責任分開後，兩邊的迭代速度都能加快。不需要因不同端邏輯修改而影響到另一端服務與邏輯在各前端不同步問題(API由後端掌控，非前端自行處理避免未來大改或者業務大改)

  • 隱藏對外暴露風險
    前端不會針對底層API服務做請求，而是向BFF做請求，而BFF在與底層服務做請求與組合，通常底層服務都與資料庫緊密連接，API都是核心API對於穩定性和可靠性有很大的要求，因此越少這種資訊暴露在前端越好

導入 BFF 前要想清楚的事

BFF 不是萬靈丹，導入前建議先評估:

  • 團隊規模是否夠大:如果公司產品單純，無須多個服務只有一個前端、一個後端，多一層 BFF 反而增加維運成本與部署複雜度。

  • 誰來維護 BFF:是前端團隊、後端團隊，還是獨立的平台團隊?責任歸屬不清楚，BFF 容易變成沒人想碰的孤兒服務。不過通常是後端工程師去維護。

  • 會不會變成新的瓶頸:如果所有邏輯都塞進 BFF，它自己也可能膨脹成另一個難以維護的巨石應用，失去原本輕量聚合層的初衷。

  • 重複程式碼的風險:多個 BFF 之間可能會有相似的邏輯(如認證、Logging)，需要透過共用套件或平台工具來降低重複。

  • 前端服務即時性問題:BFF就是再多一層後端服務聚合前端所需，因此在Response時間上不會比單體服務或者直接訪問底層API來的快，這場景也須謹慎評估。

  • 鏈路追蹤處理:即使BFF針對前端不會有前端相互耦合，但對於核心的底層後端服務也是耦合的，多個BFF會與底下多個底層後端服務耦合，所以鏈路追蹤需要做好監控與管理。

結論

BFF 的本質，是把「前端專屬的資料整合與轉換邏輯」從通用後端中抽離出來，讓每個前端都能擁有一支貼身訂製的 API。它特別適合:- 產品同時支援多種前端平台，且需求差異明顯- 後端已經微服務化，前端常需要串接多支 API 才能組出一個畫面- 團隊夠大，能夠負擔多一層服務的維運成本
