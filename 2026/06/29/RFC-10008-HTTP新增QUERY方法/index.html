RFC 10008: HTTP新增QUERY方法

發表於2026-06-29|更新於2026-07-30|BackendAPI Design
|瀏覽量:

科技趣事 - PR不是免費的

SQLite 的作者 Richard Hipp 在訪談中解釋了為何 SQLite 一律拒絕外部提交的 PR。

他的理由很直接：「免費」的貢獻，對維護者來說從來都不免費。

他引用了一個說法來比喻這件事：

「Free 有兩種意思——免費啤酒，和言論自由。但還有第三種 Free：免費的小狗。『瞧，我這裡有隻免費的小狗送給你！』」

提交一個 PR，就像有人送你一隻免費的小狗。

表面上是禮物，但從你收下的那一刻起，責任就轉移了。你不能把牠丟掉，道德上你有義務照顧牠，直到牠自然死亡。一天下來，你的小屋裡多了一隻狗。一年下來呢？
所以 Richard Hipp 的答案很簡單：「我不要任何免費的小狗。」

自己很有感觸，程式開發維護才是最大的挑戰。任何功能都是一段需要長期維護、測試、相容的程式碼。也是身為工程師更上一層樓的硬實力。

RFC 10008: HTTP新增QUERY方法

2026 年 6 月，IETF 正式發布了 RFC 10008，為 HTTP 帶來了一個期待已久的新方法：QUERY。解決了後端工程師一定都會遇到的API開發問題

問題從哪裡來？

在 RESTful API 的世界裡，我們習慣用 GET 來取得資料：

對於簡單的篩選條件，這樣完全沒問題。但當查詢邏輯變得複雜深層巢狀結構、多條件組合、或是包含特殊字元的參數，URL 就會變得又長又難讀，甚至可能碰到瀏覽器或伺服器的字元長度限制。

為什麼不用 GET + Request Body？

理論上，HTTP 規範並沒有明確禁止 GET 帶有 request body，但也明確表示不建議這樣做。舉例:
篩選符合以下條件的商品：
「分類是電子產品，且價格在 1000 到 5000 之間 或 庫存大於 50 ，且 標籤必須包含 ‘sale’。」

用GET URL就會像這樣，前端工程師寫得痛苦，後端工程師開發時更容易出錯。

實際上，很多 client、proxy 和 web server 對於帶有 body 的 GET 請求行為不一致——有的直接拒絕，有的忽略 body，有的才正確處理。放在企業防火牆後面的使用者可能完全無法使用你的 API。

那 POST 呢？

不過還是有些缺點POST 在語意上代表「建立資源」(自己是以建立事件角度來帶看說服自己XD)或「觸發非冪等操作」，用來做查詢會讓 API 語意變得不清晰。

  • Proxy 和 middleware 無法自動識別這是一個唯讀操作
  • 自動快取無法生效，此外CDN、Gateway、AP在快取上會有一些瓶頸與挑戰。

期待的QUERY 方法

RFC 10008 定義的 QUERY 方法，正是為了填補這個空缺：

概念上很直白：QUERY 就是一個可以帶 body 的 GET。它同時具備：

特性 GET QUERY POST
Safe（唯讀） Y Y N
Idempotent（冪等） Y Y N
支援 Request Body N Y Y
可快取 Y Y 有限制(尚未確定)

CORS Preflight（Section 4 Security Considerations）

這是一個很容易踩到的坑，RFC 原文明確說明：

A QUERY request from user agents implementing Cross-Origin Resource Sharing (CORS) will require a “preflight” request, as QUERY does not belong to the set of CORS-safelisted methods.

QUERY 不在 CORS 安全清單內，瀏覽器一律會先送 OPTIONS preflight 請求，做前後端分離時必須確認後端有正確處理。

錯誤碼對照（Section 2.1）

RFC 也明確定義了各種錯誤情境對應的 HTTP 狀態碼：

情境 狀態碼
缺少 Content-Type 400 Bad Request
Content-Type 不支援 415 Unsupported Media Type
Content-Type 正確但內容格式錯誤 400 Bad Request
格式正確但查詢語意無法執行（如 SQL 查不存在的表） 422 Unprocessable Content
不支援 client 要求的回應格式 406 Not Acceptable

使用前需要注意什麼？

QUERY 是新方法，目前支援度還相當有限。在採用前有幾點要考慮：

  • 現有的 GET 查詢不需要強制遷移，如果 URL 參數夠用就繼續用
  • 如果查詢結果需要分享連結或書籤，繼續用 GET，QUERY 不支援這個場景
  • 各種 client、proxy、web server 可能尚未支援，要做好相容性測試
  • 快取 key 邏輯比 GET 複雜，需要同時考慮 URL、body 和 Content-Type
  • CORS preflight 一定會觸發：後端需要在 CORS 設定中明確允許 QUERY method

FastAPI 支援現況

如果你正在使用 FastAPI，想必會想知道能不能直接用 @app.query(...) 來定義路由。

答案是：目前還不行，但社群正在推進中。

FastAPI 的 GitHub 上已有相關 issue（#12965）追蹤這個功能，目前的卡點在於 OpenAPI 規範本身。FastAPI 的文件生成依賴 OpenAPI，而 OpenAPI 需要先正式支援 QUERY 方法，FastAPI 才能跟進。好消息是 OpenAPI 3.2 已經合併了對 QUERY 方法的支援，根據Issue現況要在等Swagger UI 支援 OpenAPI 3.2 的 QUERY與FastAPI 跟進支援。

小結

HTTP QUERY 方法填補了 GET 和 POST 之間長期以來的語意空缺。它讓複雜查詢可以用正確的方式表達：帶有結構化 body、明確是唯讀且冪等、並且可被快取。讓API設計更具體，我自己是舊的API 沿用POST不調整，但未來新的API會用QUERY 來開開看，期待FastAPI支援的到來。
