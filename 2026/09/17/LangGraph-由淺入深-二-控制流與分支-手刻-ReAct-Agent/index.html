動手前的兩個常見誤解

在動手之前先釐清兩個常見誤解

LLM 本身完全不會呼叫任何 function，它連「呼叫」這個動作都做不到，它只會生成文字。

真正的流程是:

  1. 你把工具的 JSON schema(名稱、描述、參數)跟 messages 一起送進 API
  2. LLM 判斷「這句話需要用工具」，生成一個 tool_use block(仍然只是文字生成，只是格式特殊)
  3. 你的程式碼解析這個 block，真正去執行對應的 Python function
  4. 你把執行結果包成 tool_result，塞回 messages，再呼叫一次 API， LLM 看到結果生成最終回答

所以整個 Agent 迴圈是「程式 ⇄ LLM API」，LLM 只負責決策，執行永遠是程式碼在做的。

條件邊 (Conditional Edges)

綁訂完工具後，由於edge 都是固定的。但 Agent 的核心需求是「依照 LLM 的決策，動態決定去哪」使用者可能查台北或東京，所以是動態的，因此要使用到LangGraph最重要的概念conditional_edges(條件邊)。我需們要設置一個條件邊邏輯，當llm回傳回來的Response tool_calls不為空，代表要做對應的tool使用決策，如果為空代表已經整理好答案直接結束循環

其實這邊流程會是:LLM 決策 → 如果要用工具就去執行 → 執行完把結果丟回去讓 LLM 再看一次 → 再決策，如此反覆直到不需要工具為止。

迴圈是靠 edge「繞回去」實現的，不需要自己寫 while 迴圈。也是LangGrapg強大之處都幫你處理好了。route 函式吃 state，回傳一個字串告訴 LangGraph 接下來去哪個 node，目的地是動態算出來的，不是寫死的。

接下來開始建構圖，並添加Node與設置Edge

add_conditional_edges 的第三個參數在幹嘛?

  • 第一個參數:規則套用在哪個 node 執行完之後
  • 第二個參數(route):回傳一個「標籤字串」，不是 node 名字
  • 第三個參數:對照表，把標籤翻譯成真正的 node 名字

這樣寫的好處是 route 函式跟 node 命名解耦，以後改 node 名字，只要改對照表，不用動 route 函式內部邏輯。

完整的手刻 ReAct Agent

結果

問「台北天氣如何?風速又如何?」，你會看到訊息序列變成:

human → ai(一次帶兩個 tool_calls) → tool → tool → ai(彙整回答)

ToolNode 內建就支援一次執行多個 tool_calls，不用自己寫迴圈去跑。而且加新工具時,只有 tools list 跟 bind_tools(tools) 需要改，route 跟圖結構完全不用動，這是良好抽象設計的體現再次體現LangGraph強大之處。

小結

  • Tool calling 的本質是「LLM 生成決策文字，你的程式碼負責執行」
  • Conditional edge 讓圖的走向動態化，Agent 迴圈靠 edge 繞回去實現
  • ToolNode 內建支援 parallel tool calls
  • 用對照表讓路由邏輯跟 node 命名解耦
