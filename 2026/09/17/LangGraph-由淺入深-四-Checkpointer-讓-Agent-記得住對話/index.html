LangGraph 由淺入深(四):Checkpointer,讓 Agent 真正記得住對話

沒有記憶的 Agent

每次 invoke() 都是全新的一次呼叫。LLM不會有記憶這機制，可以從下面程式驗證這件事情

result

第二次呼叫，LLM 完全不知道「風速」問的是哪個城市，因為 messages 只有這次的內容，沒有第一次問答的脈絡。這是 LLM 沒有記憶的本質，每次都是從頭讀一次你傳進去的文字。

Checkpointer 解決什麼問題

沒有 checkpointer:

invoke() → 圖跑完 → 結果丟給你 → state 消失。

加上 checkpointer:

invoke() → 每跑完一個 node，自動存下當下完整 state → 下次 invoke 用同一個 thread_id，自動讀回上次狀態，疊加這次新內容。

關鍵是 thread_id，對話的識別碼。同一個 thread_id 的多次呼叫，狀態會累積延續;換一個 thread_id，就是全新對話，互不干擾(多用戶場景的隔離機制)。

最簡單的用法直接使用LangGraph MemorySaver

compile() 這一行加上checkpointer，其餘不須要改State、node、edge 完全不用動，持久化是橫切關注點，不該污染業務邏輯，LangGraph在這方面設計是真的職責做得很好。然後呼叫時要多帶一個 config:

LangGraph 自動把 thread_id="user-1" 之前存的所有訊息讀出來，跟新訊息合併(靠 add_messages reducer)，再一起丟給 LLM，LLM 才知道「風速」問的是台北。其實簡單來說就是文字接龍概念。

MemorySaver 只存在 RAM，正式環境會使用 SqliteSaver 或 PostgresSaver，甚至向量資料庫來保存。

另外還能回溯到某個歷史 checkpoint，重新從那個點開始執行，這在除錯(「這一步到底哪裡出錯」)跟實驗性分支很有用，這種方式可以不必對話從頭開始，而是有問題地方進行調整，對於工程優化很有幫助這部分有機會後面會細講，這邊就暫時不講這麼深入。

小結

  • Checkpointer 讓 thread_id 底下的完整對話歷史自動被存取，不用自己手動拼接
  • 持久化跟業務邏輯完全解耦，只需要改 compile()
  • Time travel 建立在「逐步存 state」的基礎上，不是只存最終結果
