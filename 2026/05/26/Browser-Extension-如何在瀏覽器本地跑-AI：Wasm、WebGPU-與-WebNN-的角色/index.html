Browser Extension 的 AI 架構怎麼選？

在設計 AI Browser Extension 時，最常見的做法大致有兩種：串接第三方模型 API，或讓使用者自行架設推論伺服器。

方向一：串接第三方模型 API

優點：

  • 開發速度快，不必自行部署模型與推論伺服器。
  • 不必處理模型量化、硬體相容性與推論效能調校。
  • 系統架構較單純，通常也能取得較好的模型品質。

限制：

  • 需要持續付費，用量成長後費用可能相當可觀。
  • 依賴網路，離線時無法使用。
  • 受到 Rate Limit、服務穩定性與供應商政策影響。
  • 敏感資料必須傳送到第三方，可能不符合企業隱私或法規要求。
  • Extension 仍須妥善保護 API Token、限制權限並避免意外外洩，不能把資安責任完全交給供應商。

方向二：自架推論伺服器

優點：

  • 使用量大時，長期成本可能低於按次計費的第三方 API。
  • 資料可以保留在企業或使用者控制的環境中。
  • 可自行選擇、量化與微調模型，掌握部署策略。

限制：

  • 需要準備伺服器、模型、推論 runtime 與部署流程，技術門檻較高。
  • GPU、記憶體、儲存空間與電力成本不可忽略；降低模型參數量或量化也可能影響品質。
  • 必須處理伺服器未啟動、連接埠錯誤、版本不相容與跨來源請求等問題。
  • 需要自行維護驗證、更新、監控、資安與後端服務。

那有沒有第三條路，讓部分 AI 工作直接在瀏覽器執行？這正是 WebAssembly、WebGPU 與 WebNN 能發揮作用的地方。

在瀏覽器本地執行 AI

裝置端推論不是一次解決所有問題的魔法，但它能在特定場景中降低伺服器依賴。

對使用者的好處：

  • 模型與必要資產完成下載及快取後，部分功能可以離線使用。
  • 資料可留在本機處理，降低上傳敏感內容的需求。
  • 音訊、影片與圖片不必來回傳輸，有機會降低延遲。

對開發者的好處：

  • 部分功能不需要後端推論服務。
  • 將運算分散到使用者裝置，有機會降低伺服器的算力與頻寬成本。
  • 可以設計「本機優先、雲端備援」的混合架構。

但本地推論也會把模型下載時間、瀏覽器相容性、裝置效能、記憶體占用與耗電問題帶到前端。使用者的硬體差異很大，因此仍要準備 fallback，而不是假設每台裝置都能順利執行。

瀏覽器中的 AI 推論如何運作？

AI 模型通常由 Python、C++ 等生態系建立，但瀏覽器中的推論通常會透過 JavaScript API 與專用 runtime 執行：

  • JavaScript 或 WebAssembly 使用 CPU。
  • WebGL 或 WebGPU 使用 GPU。
  • WebNN 將神經網路運算交給瀏覽器與作業系統，選擇 CPU、GPU 或 NPU 等可用後端。

這裡要特別釐清：不是把整個模型一律「轉成 .wasm」。更常見的情況是將推論引擎或原生程式編譯成 WebAssembly，再由它載入 ONNX、GGUF 或其他格式的模型權重。

WebAssembly：相容性與可攜性優先

WebAssembly（Wasm）是一種適合瀏覽器載入與執行的二進位指令格式。C、C++、Rust 等程式可以編譯成 Wasm，讓既有的推論引擎移植到 Web 環境。

在 Web AI 中，Wasm 通常使用 CPU 執行，適合 OCR、小型音訊模型、影像處理或其他規模較小的工作負載。

優點：

  • 瀏覽器支援成熟，可攜性高。
  • 適合移植既有的 C/C++/Rust 推論程式。
  • 在瀏覽器沙箱中執行，部署方式比原生程式單純。

限制：

  • 主要依賴 CPU，對大型生成式模型可能太慢。
  • 模型仍會占用下載流量、記憶體與儲存空間。
  • 效能取決於工作負載、SIMD、執行緒及瀏覽器實作，不能簡化成「所有裝置都能順跑」。

WebGPU：把平行運算交給 GPU

WebGPU 讓網頁程式存取現代 GPU 的運算能力。對矩陣與張量等高度平行的工作負載而言，WebGPU 通常比純 CPU 推論更有優勢，也是目前瀏覽器端執行較大型模型的重要技術。

優點：

  • 適合大量平行運算，可明顯加速部分 AI 模型。
  • 不必把資料傳到遠端伺服器。
  • 能支援比純 Wasm CPU 路徑更大型的工作負載。

限制：

  • 效能仍受模型、GPU、驅動程式、瀏覽器與資料搬移成本影響，未必都能接近原生 App。
  • WebGPU 需要安全來源，正式網站通常必須使用 HTTPS。
  • 瀏覽器與平台支援仍有差異，必須做 feature detection 與 fallback。

WebNN：讓瀏覽器選擇 CPU、GPU 或 NPU

Web Neural Network API（WebNN）是一項新興 Web 標準。它提供神經網路運算介面，讓瀏覽器與作業系統依裝置能力使用 CPU、GPU，或專門處理 AI 工作負載的 NPU。

這對新款筆電與行動裝置很重要，因為 NPU 通常比高功耗 GPU 更適合持續執行某些 AI 工作負載。WebNN 的價值不只是「直接呼叫 NPU」，而是讓框架透過統一介面使用平台提供的最佳硬體後端與最佳化能力。

優點：

  • 有機會取得較好的效能與能源效率。
  • 可以利用 GPU、NPU 等平台原生加速能力。
  • 開發者不必為每一種硬體各寫一套底層實作。

限制：

  • 標準與瀏覽器實作仍在發展中。
  • 支援度取決於瀏覽器、作業系統、驅動程式與硬體。
  • Microsoft 文件目前仍把 GPU 與 NPU 支援列為預覽，不建議直接假設可用於所有正式環境。

常見的裝置端 AI 加速器包括：

  • Apple Neural Engine（Apple Silicon 與行動裝置晶片）
  • Intel NPU（新款 Intel 平台）
  • Qualcomm Hexagon NPU / AI Engine（部分 Windows on Arm 與 Android 裝置）

三種技術怎麼選？

技術 主要硬體 適合場景 注意事項
WebAssembly CPU OCR、音訊處理、小型模型、跨裝置 fallback 相容性高，但大型模型可能較慢
WebGPU GPU 圖像模型、生成式 AI、平行張量運算 需檢查瀏覽器、GPU 與驅動支援
WebNN CPU / GPU / NPU 希望使用平台原生 AI 加速的神經網路 API 與支援狀態仍在發展中

實務上不一定三選一。較穩健的產品通常會建立多層 fallback：

常見框架：不用自己處理所有底層細節

框架 特色 適合場景

ONNX Runtime Web 執行 ONNX 模型，支援多種 Web 後端 通用模型部署與跨平台推論

選擇框架前，應先確認模型授權、輸入輸出格式、模型大小、瀏覽器支援、初始化時間與目標裝置的記憶體限制。

結論

隨著量化與輕量化模型進步，瀏覽器本地推論已經能處理 OCR、語音辨識、翻譯、分類、影像分析，甚至部分生成式 AI 任務。它的價值不只是速度，也包含隱私、離線能力與降低伺服器成本。

不過，本地 AI 並不會完全取代雲端模型。裝置效能差異、模型下載大小、瀏覽器相容性與更新策略仍是實際產品必須處理的問題。對 Browser Extension 而言，更實用的方向通常是混合架構：能在本地完成的工作優先使用 Wasm、WebGPU 或 WebNN；需要大型模型品質或本機效能不足時，再切換到遠端 API。

這三項技術可以簡單理解成：WebAssembly 提供可攜的 CPU 執行環境，WebGPU 提供 GPU 平行運算能力，而 WebNN 嘗試提供統一的神經網路硬體加速介面。理解它們各自的角色，才能依模型、裝置與業務需求做出合適的架構選擇。
