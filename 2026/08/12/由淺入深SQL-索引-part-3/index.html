SQL Function Index：為什麼 lower(name) 會讓索引失效？

Function Index 是什麼？

Function Index 的概念很直覺：不是只把「欄位原始值」放進 index，而是把「欄位經過某個 function 或 expression 計算後的結果」放進 index。

原因是 index 裡保存與排序的是原始 name，不是每個 name 經過 lower() 後的結果。對資料庫來說，name 和 lower(name) 是兩種不同的搜尋條件。

Function Index 的限制與危險性

Function Index 不是任何 function 都能安全使用。放進 index 的 function 必須是 deterministic，簡單來說就是只要輸入值一樣，輸出結果就一定要一樣，而且結果不會隨時間或外部狀態改變。

PostgreSQL稱為IMMUTABLE

建立索引時

然後過了一年查詢結果找不到，嚴重的正確性問題查詢不會報錯，只會安靜地漏資料這很可怕，因為你可能完全不會發現。

Over-Indexing：Function Index 篇

Function-based index 特別容易造成 over-indexing，因為同一個不分大小寫搜尋的需求，程式裡如果有的地方寫LOWER(last_name)、有的地方寫 UPPER(last_name)，就會逼你建兩個索引來支援同一種查詢邏輯

例子
需求:不分大小寫搜尋姓氏
假設沒規範那你與你的同事會有兩種寫法

兩種不同的 expression因此可能需要建立兩個索引。

這就是 Function-based Index 容易造成 Over-Indexing 的原因。要避免這種問題，團隊要先訂好固定查詢寫法，例如統一使用 LOWER() 或統一使用 UPPER()。
另外如果有使用 ORM，也要特別注意 ORM 是否會自動注入隱含的 LOWER() 或 UPPER()，導致查詢 expression 和 index 定義對不上。

其實建議優先索引原始資料，只有真正需要時才用 function index，預設應該優先在原始欄位建索引

小結

Function Index 解決的是「查詢條件不是原始欄位，而是某個 expression」的問題。像 WHERE lower(name) = 'alice' 這種查詢，資料庫不能直接把它當成 name 欄位索引來使用，因為索引裡排序的是原始 name，不是 lower(name) 的結果。

這篇的重點可以收斂成三句話：

  • 查詢條件的 expression 必須和索引定義一致，Function Index 才能派上用場。
  • 放進 index 的 function 必須穩定且可預期，否則可能造成索引結果與真實資料不一致。
  • Index 設計應該從 Query Pattern 出發，用最少的 index 支援最重要的查詢，而不是看到 WHERE 條件就盲目加索引。

商業邏輯會變，查詢也會變；如果不確定某個 index 能不能長期服務重要查詢，寧可先觀察實際 query pattern，再決定是否建立。好的 Index 設計，是在讀取效能、寫入成本、儲存空間和維護複雜度之間取得平衡。
