SQL 複合索引：回表成本、Concatenated Keys 與索引順序

發表於2026-08-12|更新於2026-08-27|Database
|瀏覽量:

還記得上一篇「SQL 索引入門：B+ 樹、葉節點與查詢加速原理」提到的葉節點鏈表掃描與回表撈取資料會影響速度問題嗎？這邊快速複習一下整個 Flow

flowchart TD
    A[開始 Index Scan] --> B[Tree Traversal<br/>從 root 找到 leaf]
    B --> C[找到第一筆符合條件的<br/>index entry]
    C --> D{查詢需要的欄位<br/>都在 index 裡嗎?}
    D -->|是| E[Index Only Scan<br/>直接從 index 回傳資料]
    D -->|否| F[依照 ROWID / RID<br/>回 table 找 row]
    F --> G[讀取完整資料列]
    G --> H{還有其他符合條件的<br/>index entries 嗎?}
    H -->|有| I[沿著 leaf linked list<br/>繼續掃描下一筆]
    I --> D
    H -->|沒有| J[回傳查詢結果]

Concatenated Keys(複合索引)

舉個例子需要設計一個公司員工表

employee_id 的唯一性，資料庫不需要遍歷整個索引葉節點，只要沿著索引樹往下找就能確定唯一的一筆資料，效率很高。

假設有一張表，公司因為成長合併了其他家公司，表中需要新增subsidiary_id

原本是查詢employee_id現在變成subsidiary_id雙主鍵，因此需要加複合式索引

查詢時就會用上索引

很多人以為複合索引是建立兩個索引，其實是錯的他是一體的。單一的 B-Tree 結構，資料是以欄位順序的「組合值」來排序與儲存的。

複合索引失效查詢

但是如果查詢條件為以下就會失效走全局掃描。

因為葉節點subsidiary_id被分散在各地，索引是以employees列好的順序開始找，索引用索引搜尋，但用subsidiary_id找的話，會不知道路徑要從哪找，所以就會全局掃描。

B-tree 的內部節點(branch node)，只記錄了 employee_id 的分界值，用來做「往左走還是往右走」的路由判斷。因為索引是先依 employee_id 排、subsidiary_id 只是次要排序，所以樹狀結構裡完全沒有任何一個內部節點是依 subsidiary_id 的值來分岔的。

複合索引與多個單一索引

上一節提到複合索引，那如果把 employees 與 subsidiary_id 各自建立單一索引，也能加快嗎？答案是可以的。

雖然加一個額外的 subsidiary_id 索引也能讓兩種查詢都變快，但單一個順序正確的複合索引更好。上一篇「SQL 索引入門：B+ 樹、葉節點與查詢加速原理」也提到：索引本身需要維護，因此複合索引可以節省儲存空間，也省下第二個索引對 insert/update/delete 帶來的額外負擔。

複合索引欄位順序

複合索引欄位順序，決定它能不能被有效利用，因此判斷依據如下

  • 最常查詢的欄位放前面

那index肯定是這樣設計

  • 多唯一性擺前面
    性別欄位只有兩種 -> M/F
    user_id多種 -> 1、2、3….1000000

查詢索引順序，假設定義了複合式索引

複合索引 (A, B, C) 查詢有效性分析

查詢條件 (WHERE) 索引是否有效 原因說明
A 有效 包含最左側欄位 A
A, B 有效 從最左側開始，連續包含 A 和 B
A, B, C 有效 完整匹配整個複合索引的所有欄位
B 無效 缺少最左側欄位 A，無法使用索引排序
C 無效 缺少前置欄位 A 與 B
B, C 無效 雖然欄位連續，但依然缺少起頭的 A

因此複合索引欄位順序，決定它能不能被有效利用。後端工程師在做設計時須考量實際業務邏輯與查詢的關係。重點就是「容易被查詢的擺前面，不常或者不被搜尋擺後面」定義索引順序。

複合索引讓速度變更慢了

改索引不是只影響你想優化的那個查詢，而是會影響這張表上所有查詢。

因為 last_name 根本不在這個索引裡，索引只能先抓出 id 為 30 的分公司所有員工的 ROWID(這裡有 25 個 ROWID)， 再對這 25 筆逐一回表去檢查姓氏是不是 WINAND

索引雖然幫你快速鎖定，但你還要對這 25 筆逐一做「回表」(隨機 I/O)，這比循序讀完整張表還要慢。這正是「SQL 索引入門：B+ 樹、葉節點與查詢加速原理」和本文開頭一直在鋪的慢索引兩要素：索引範圍太寬 + 逐筆回表。因此數據量非常大時，這種查詢就會導致資料庫效能瓶頸，甚至比不加索引還糟糕。

資料庫非常聰明，當它發現你在做全表掃描時，會一口氣把後面幾十個Block/Page提早載入到記憶體。隨機 I/O 讓資料庫無法預測你下一步要讀哪裡，每一次都必須老老實實去翻實體磁碟。索引有沒有用到不是重點，重點是索引幫你排除掉了多少「不相關的資料」，而回表次數越多，索引就越慢

Index Only Scan

如果想避免回表可以使用Index Only Scan，目前已知這個例子是回表所引起效能問題，那就將更多資訊儲存到index避免去table回表，

last_name、first_name、phone_number 通通都已經在索引裡了，不管檢查結果通過還是沒通過，都不需要再跑去資料表撈資料，因為索引已經有查詢需要的全部欄位。本來25 次(每筆都要回表才能檢查 last_name,也才能拿到 first_name、phone_number)，現在0次直接去index裡面取得。

Index Only Scan 雙面刃

但這也要權衡就是了，提到很多次index也是需要空間的，此外加進index代表table存一份，index存一份就很浪費，且連帶CUD速度下降。

維度 獲得的好處（Benefits） 付出的代價（Costs）
效能 (Performance) 查詢變快（Read 提升）
• 省去回表（Table Lookup）
• 將隨機 I/O 轉為順序 I/O		 寫入變慢（Write 降級）
• INSERT / UPDATE / DELETE 變慢
• 需同步維護與更新 B+Tree
資源 (Resource) 降低 Disk I/O
• 直接在索引頁完成讀取
• 減少磁碟隨機讀取次數		 空間膨脹 (Storage)
• 索引體積變大
• 佔用更多硬碟空間與 Buffer Pool 記憶體

小結

複合索引不是把多個單欄位索引疊在一起，而是在同一棵 B+Tree 裡，依照欄位順序組成排序規則。因此它能不能派上用場，關鍵在於查詢條件是否符合最左前綴原則，以及索引是否真的能縮小掃描範圍。

這篇的重點可以收斂成三句話：

  • 複合索引的欄位順序會決定資料庫能不能有效定位資料。
  • Index lookup 變慢時，常見瓶頸不是 tree traversal，而是 leaf scan 範圍過大與逐筆回表。
  • Index Only Scan 可以避免回表，但代價是索引變大、寫入維護成本也會上升。
