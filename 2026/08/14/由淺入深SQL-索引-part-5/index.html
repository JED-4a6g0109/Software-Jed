SQL Partial Index：用部分索引優化軟刪除與高頻查詢

發表於2026-08-14|更新於2026-08-27|Database
|瀏覽量:

Partial Indexes

目前討論的都是索引該包含哪些「欄位」，而索引其實也能包含「列」，這稱為 partial index(PostgreSQL 用語)。

例子
在核心的表中，通常會使用軟刪除避免誤刪無法拯救資料

應用程式幾乎所有查詢都是 WHERE deleted_at IS NULL(找還活著的資料)，已刪除的資料極少被查。資料庫用久了，deleted_at IS NOT NULL 的資料可能佔一大半，但索引可以完全排除它們。

這種索引設計好處是即使資料表持續無限成長，因為索引裡只包含已刪除資料，所以索引增長會相較慢節省空間又能提升查詢效能。這種設計可以以查詢常帶有某個「值分佈極度不均勻」的固定條件，而你只在乎少數那一邊的情境

時間與資料量與索引

索引的欄位順序缺陷，不是「資料量大了才出現」，而是「資料量小時損耗不明顯，資料量放大後損耗被同步放大」。

如果Query 語法這樣下，資料量小時耗時不會明顯凸顯出來，所以很常被忽略索引有設計好

但是隨時間或資料量一大，這是一個很嚴重的效能瓶頸，回顧索引是一條鏈的概念，先依 section 排，同 section 內再依 id1 排，同 id1 內才依 id2 排。當查詢只給了 section 和 id2、沒給 id1 時，資料庫在「同一個 section 內」看到的 id2 順序其實是亂的(因為排序權被 id1 卡住了)，所以 id2 只能退化成 filter，逐筆比對。
在「SQL 範圍查詢索引設計：等值條件、Access Predicate 與欄位順序」裡提到，當中間欄位沒有被查詢條件使用時，會破壞後續欄位成為 access predicate 的資格。

因此有些系統突然變慢要先檢查方式是看執行計劃裡的 Predicate Information，如果原本該當 access 的欄位變成 filter，就代表索引順序跟查詢已經對不上了。業務邏輯改變是很常有這種情況的，索引原本是為了別的查詢設計的，中間欄位剛好卡住了你現在這個查詢

關鍵落差在於SCALE_SLOW 在高負載下，回應時間是「沒有背景負載時」的 30 倍。filter predicate 本來就要多掃資料、多耗 CPU，平常一條查詢跑的時候還好，但當很多條查詢同時搶 CPU、I/O 資源時，會被同時放大很多倍。

小結

Partial Index 的價值，不只是「索引變小」而已，而是把索引真正留給高頻、固定、值得優化的查詢條件。像軟刪除場景裡，應用程式大多只查 deleted_at IS NULL 的資料，那就不一定要讓已刪除資料也佔據索引空間。

開發實務上建議：

  • 開發環境測不出這個問題：開發環境通常只有你一個人在跑查詢，負載趨近於零，filter predicate 的缺陷很容易被掩蓋。
  • 正式環境比開發環境慢，不代表硬體不夠力：很多人直覺覺得「正式環境硬體更好，應該更快」，但正式環境有真實的並發負載，會把索引設計的缺陷放大出來。

加硬體不等於解決回應時間問題。加硬體通常只能提升「同時處理多少請求」的能力，也就是吞吐量，但沒辦法讓慢查詢本身變快。真正該優先做的，是先檢查索引設計對不對。

  • 別只信任表面測試，要去看執行計劃：仔細檢查 Predicate Information，確認條件是 access 還是 filter，更能提早抓到索引順序和查詢模式不匹配的問題。

這篇的重點可以收斂成三句話：

  • Partial Index 適合用在固定條件、高頻查詢、資料分佈明顯不均的場景。
  • 業務邏輯改變時，原本合理的索引順序可能會變成效能瓶頸。
  • 遇到正式環境慢查詢時，不要只看有沒有用 index，也要看條件到底是 access predicate 還是 filter predicate。
