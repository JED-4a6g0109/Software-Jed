SQL 範圍查詢索引設計：等值條件、Access Predicate 與欄位順序

範圍查詢(>、<、BETWEEN)的索引欄位順序

當 WHERE 子句同時有範圍條件和等於條件時，索引裡兩個欄位的先後順序會嚴重影響效能。

前面「SQL 索引入門：B+ 樹、葉節點與查詢加速原理」和「SQL 複合索引：回表成本、Concatenated Keys 與索引順序」其實已經一直在講兩件事：

  • 縮小掃描範圍：讓資料庫在 B+Tree 裡更早定位到真正需要讀的 index entries。
  • 掃完再逐筆比對：資料已經被掃出來了，但還要一筆一筆檢查條件，最後再把不符合的資料丟掉。

在資料庫執行計劃裡，這兩件事通常會對應到兩個詞：

  • 存取條件（Access Predicate）：真正用來定位索引掃描範圍的條件。它會決定 B+Tree 從哪裡開始掃、掃到哪裡停，因此能直接減少需要讀取的 index entries。
  • 過濾條件（Filter Predicate）：資料已經被掃出來之後，才逐筆套用的條件。它可以把不符合的資料排掉，但不能縮小一開始的索引掃描範圍。

簡單講，Access Predicate 是「少掃一點」，Filter Predicate 是「掃完再丟掉」。這篇會一直圍繞同一個問題：索引欄位順序怎麼排，才能讓重要條件變成 Access Predicate，而不是退化成 Filter Predicate。
例子
查27 分公司、生日在 1971/1/1~1/9 之間的員工

只在 DATE_OF_BIRTH 上建索引時，掃描範圍就是指定的日期區間。沒啥太大問題

但加入第二欄位後，問題浮現理想的索引要涵蓋兩個欄位，但欄位順序該怎麼排?

兩種索引選擇

  • index(date_of_birth,subsidiary_id)
    date_of_birth 是範圍，可以當 access predicate，但 subsidiary_id 因為排在範圍欄位後面，只能逐筆掃描比對，走 Filter Predicate,所以整體效能較差。需要逐掃瞄葉節點。

  • index(subsidiary_id,date_of_birth)
    subsidiary_id 是 equal，分支節點就能直接定位到 27 分公司這一段範圍(不用像 date_of_birth 那樣掃過好幾個葉節點)，而在這段範圍裡，資料本身已經依 date_of_birth 排序好了，所以 date_of_birth 的範圍也能直接拿來當起點精準定位掃描區間，而不是Filter Predicate，兩個條件都變成 access predicate，共同決定同一個掃描範圍的起點和終點。

所以索引欄位順序看條件種類，「等於條件放前面，範圍條件放後面」，才能讓資料庫在索引樹的分支節點就排除不相關資料，大幅縮小掃描範圍。

Indexing LIKE Filters

LIKE 運算子常造成意料之外的效能問題，因為有些搜尋詞能有效利用索引，有些不能，取決於%擺哪，LIKE 過濾條件在樹狀走訪時，%之前的字元能拿來當 access predicate，後面的字元只能當 filter predicate，不會縮小掃描範圍。因此如果開頭第一個是%，如果沒有其他條件能提供 access predicate，資料庫才必須全表掃描。

為什麼兩個 Range 條件無法都當 Access Predicate

索引設計最常見的問題之一，每個欄位各建一個索引比較好，還是把 WHERE 子句所有欄位建成一個索引比較好? 大多數情況答案很簡單，都選擇單一的多欄位索引，但有例外

兩種範圍查詢

索引本質上是一條鏈結串列

但查詢需要「兩個」獨立範圍條件同時成立，而兩個範圍搜尋條件，理論上需要像棋盤的 X、Y 兩軸一樣才能圈出一個目標範圍,這是一個二維的需求。但索引只有一維的排序能力。

單一多欄位索引

最簡單的解法為接受一個變 filter這個做法，因此兩個 range 條件裡，只能有一個當 access predicate(真正縮小掃描範圍)，另一個只能退化成 filter predicate(掃描途中逐筆篩選，不縮小範圍)。只是這邊要將多選擇性擺在索引前面，來縮小掃瞄範圍。

選擇性 = 符合條件的資料筆數 ÷ 資料表總筆數。篩選條件實際能刷掉多少比例的資料

如果 last_name < ‘M’ 大約篩掉一半(50%)，而 date_of_birth < 1980 篩掉 90% 的資料，那就該把 date_of_birth 放第一欄

Index Merge

除了單一多欄位索引還能使用Index Merge概念來解決。各自建了兩個獨立索引

Index Merge步驟為
1.各自掃描: idx_name 和 idx_dob 各自產生一組 ROWID 清單
2. 取交集: 兩組清單比對,留下共同存在的 ROWID
3. 回表: 用交集結果撈出完整資料列

單一多欄位索引與Index Merge兩者差異

單一多欄位索引 Index Merge
索引樹要走訪幾次 1 次 2 次(兩棵樹分別走)
需要合併/排序 ROWID 清單嗎 不用 要(額外的 CPU + 記憶體)
回表撈資料次數 1 次(針對最終結果) 1 次(但前面多兩步工)

因此一次索引掃描比兩次快，而Index Merge 本質上是用兩次索引查找 + 一次集合運算，換取兩個條件都能各自用上索引，是一種「拿時間換精準度」的妥協，通常只有在真的沒辦法設計出好的複合索引時，才會讓優化器選這條路。

小結

範圍查詢的索引設計，核心不是「把所有 WHERE 欄位都塞進索引」就好，而是要判斷哪些條件能真正縮小掃描範圍。等值條件通常適合放在複合索引前面，因為它能先把資料定位到更小的區間；範圍條件則通常放在後面，用來決定這個區間裡的起點與終點。

這篇的重點可以收斂成三句話：

  • Access Predicate 能決定索引掃描範圍，Filter Predicate 只能在掃描後逐筆過濾。
  • 複合索引遇到等值條件和範圍條件時，通常要讓等值條件放前面，範圍條件放後面。
  • 兩個獨立 range 條件很難同時都成為 Access Predicate；Index Merge 是折衷方案，但通常會多出額外的索引掃描、合併與回表成本。

實務上設計索引時，不只要看 WHERE 子句出現哪些欄位，更要看資料庫能不能用這些欄位縮小掃描範圍。真正值得關注的是執行計劃裡條件被當成 Access Predicate 還是 Filter Predicate，這通常比「有沒有用到索引」更接近效能問題的核心。
