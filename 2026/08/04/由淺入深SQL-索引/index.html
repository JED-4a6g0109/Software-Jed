SQL 索引入門：B+ 樹、葉節點與查詢加速原理

發表於2026-08-04|更新於2026-08-27|Database
|瀏覽量:

在工作上很常用索引，但有想過為什麼有些情況下加上索引，查詢反而變慢了?這篇筆記從最基礎的索引結構開始講起，一路拆解到 B 樹如何加速查詢，最後帶到「索引為什麼會變慢」這個問題的根源。

（本篇整理自 Use The Index， Luke 的 Anatomy of an SQL Index 系列）

一、Index 是什麼：像書本目錄一樣的獨立結構

Index 是用 CREATE INDEX 語句建立的獨立資料結構，它會佔用自己的磁碟空間，並保存著被索引欄位的副本。建立索引不會改變原表(table)資料，它只是另外建立一個指向原表的新資料結構。

就像一本書的目錄，他需要佔據一頁紙張的空間，而目錄裡各篇章頁碼指向內容的實際位置。而索引關鍵在於所有條目都按照明確的順序排列。在有序資料集中尋找資料既快速又方便，因為排序順序決定了每個條目的位置。

但資料庫比一本書的目錄複雜得多，因為它必須隨時面對變動。一本書的目錄可以等下一次印刷才更新，但 SQL 資料庫必須即時處理 insert、delete、update，而且要在不大量搬移資料的前提下維持順序。

為了應付這個挑戰，資料庫結合了兩種資料結構:

  • 雙向鍊錶(doubly linked list)
  • B+ 樹

這兩種結構解釋了資料庫的大部分效能特徵。

二、葉節點（Leaf Nodes）：用雙向鍊錶維護索引順序

為什麼不直接排序 table 資料？

假設有一排按名字字母排序的書籍（A～Z）。如果現在要插入一本作者是 B 的書，而書架已經滿了：

  • 實體排序的做法：你必須把 C 到 Z 的所有書全部往後挪動一個位置，才能把 B 放進去。

但在資料庫的硬碟或記憶體中，「搬動資料」是非常昂貴的操作。只要每次 INSERT 都要大規模移動資料列，寫入效能就會變得很差。

為了解決這個問題，資料庫不會強迫 table 資料按照索引順序實體排列，而是用 index 維護一套獨立於 table 儲存位置之外的邏輯順序。

雙向鍊錶如何維持葉節點順序

雙向鍊錶會維護邏輯順序。每個節點同時記錄前一個跟後一個節點，讓資料庫可以正向或反向讀取索引。插入新 entries 時不需要搬動大量資料，只需要改幾個指標。

如果不懂鍊錶，我有寫篇關於雙向鍊錶請看此篇介紹 Jed學習筆記-鏈結串列(Linked List)，詳細拆解每個步驟。

葉節點、Block 與 Index Entry 的關係

資料庫用雙向鍊錶連接所謂的索引葉節點(leaf node)。每個葉節點儲存在一個資料庫 block(或稱 page) 裡，這是資料庫最小的儲存單位。所有的 index block 大小都一樣，通常是幾 KB。資料庫會盡量把 block 的空間用滿，塞進盡可能多的 index entries。

一個索引條目（Index Entry）通常由兩部分組成：「索引鍵（Index Key）」以及「資料指標（Pointer）」。

索引順序的維護分成兩個層面:

  1. 每個葉節點(block)內部的 index entries 排序——這樣才能在 block 內部做二分搜尋
  2. 葉節點之間透過雙向鍊錶維護的邏輯順序——這樣才能支援範圍查詢(range scan)，不用每次都重新走訪整棵樹

值得特別注意的是:table 本身的儲存方式跟 index 完全不同。Table 資料是用堆積(heap)結構儲存的，完全沒有排序——同一個 table block 裡的資料列之間沒有任何關聯，block 跟 block 之間也沒有連接。這正是 index 跟 table 最大的差異:index 有序，table 無序。

三、B+ 樹：讓索引真正變快的關鍵

葉節點在磁碟上的儲存順序是任意的——磁碟上的實體位置，跟索引邏輯順序對應的位置並不相同。

實體位置是打散的，但指標把它們串成一條看起來整齊的路，硬碟不會真的排序，而指標是幫你做邏輯排序。

如果只靠雙向鍊錶一路翻找，最壞情況得翻遍所有葉節點，查詢效率跟沒建索引沒兩樣。資料庫需要第二種結構，才能在打亂的頁碼中快速定位目標:平衡搜尋樹(balanced search tree)。

平衡搜尋樹由三種節點組成:

  • 葉節點(leaf node):最底層，實際存放 index entries 的地方(就是前面講的 block)
  • 分支節點(branch node):中間層，負責指引搜尋方向
  • 根節點(root node):最上層，只有一個

搜尋從根節點開始，依序比對每一筆 entry，直到找到第一個「大於或等於」搜尋值的項目，就沿著這個指標跳到對應的下一層節點，重複同樣的動作，直到抵達葉節點為止。

這個過程叫做樹的走訪(tree traversal)，效率非常高，原因:

  1. 樹是平衡的，所以走訪任何一個元素需要的步數都相同
  2. 樹的深度是對數成長的，資料量增加很多，深度增加得很少

這就是為什麼即使資料表有上百萬筆資料，樹查詢依然能幾乎瞬間完成。

如果很抽象可以透過B+樹網站，來建立樹來自行操作新增、刪除、查詢的整個流程會更加有感覺。

四、索引查詢為什麼會變慢：即使有 B+ 樹也一樣

長久以來有個說法認為，查詢變慢是因為「索引退化」（degenerated index），所以解法是重建索引（rebuild）。但很多時候真正的瓶頸不是樹壞掉，而是 index lookup 本來就不只做一次樹搜尋。

一次完整的 index lookup 通常可以拆成三個步驟：

  1. Tree Traversal：從 root 走到 leaf
    這一步是成本最可預期的部分。B+ 樹是平衡樹，深度會隨資料量對數成長，所以就算資料表有很多筆，從 root 找到第一個符合條件的 leaf entry 通常仍然很快。

  2. Leaf Scan：沿著葉節點鍊錶繼續掃描
    B+ 樹只能先幫你定位到「第一筆可能符合條件」的位置。如果條件會命中多筆資料，資料庫還要沿著葉節點的雙向鍊錶繼續往右讀，直到遇到不符合條件的 entry 為止。

  3. Table Access：回 table 撈完整資料列
    Index entry 通常只保存索引鍵與指向 table row 的位置（例如 ROWID/RID）。如果查詢需要的欄位不在 index 裡，每一筆命中的 entry 都還要再回 table 讀出完整 row。

所以只有第一步的成本有明確上限，第二步和第三步才是索引查詢變慢的常見原因。當符合條件的資料只有幾筆時，這個成本不明顯；但如果條件一次命中幾百筆，資料庫就得掃過幾百個 index entries，接著再依照每個 entry 的 ROWID/RID 回 table 讀幾百次資料。

更麻煩的是，table 通常是 heap 結構，資料列本身沒有按照 index key 排序。也就是說，index 裡相鄰的 entries，對應到 table 裡的 rows 不一定相鄰；它們很可能分散在不同 table blocks。結果就是：index scan 看起來是順著葉節點一路讀，但回 table 時卻可能變成大量分散的隨機讀取。這才是「明明用了索引，卻還是很慢」的真正原因之一。

小結

  • Index 是獨立於 table 的資料結構，靠 entries 的排序來加速查詢
  • 雙向鍊錶 讓葉節點維持邏輯順序，插入資料不用搬移大量資料，只需要改指標
  • 每個 block(葉節點) 內部的 entries 也是排好序的，順序維護分「block 內部」跟「block 之間」兩層
  • B+ 樹 解決了「葉節點實體位置打散」的問題，靠 root → branch → leaf 三層結構，把搜尋壓縮成對數等級的效能
