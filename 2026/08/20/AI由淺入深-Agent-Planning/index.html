Planning

前面所提女友突然向你提出要去日本，而你拿到一個任務，該怎麼想、怎麼安排步驟才能完成它?本質上就是Planning。

規劃女友的日本旅遊行程 Planning 需要的所有元素:

  • 拆解任務(訂機票/飯店/行程)
  • 線性推理(一步步想景點遊玩順序)
  • 自我審查(排完先自己挑毛病)
  • 事後反思(這次行程太趕女友不開心，下次筆記記起來)

而LLM 本身是一次生成一段回應的機制，但複雜任務往往需要多步驟、有依賴關係、可能中途要修正方向。如果沒有 Planning，Agent 就容易在長任務中迷失或繞遠路。Planning 的本質，目的是讓 Agent 從「憑感覺直接回答」進化成「像人一樣有條理地想清楚再行動，而且會從錯誤中學習」。

Subgoal Decomposition(目標拆解)

Subgoal Decomposition 做的事，就是先把大任務拆成幾個可以獨立處理的子任務，但這件事怎麼拆、拆完怎麼執行，會因為是什麼情境在規劃而完全不同。

想像同樣是規劃日本三天遊，但發生在三種不同情境下:

情境一:腦子裡想到什麼就做什麼

先查機票吧→ 查完發現這週貴到爆 →那要不要改日期?→ 改查別的日期，便宜多了→機票定案,接下來查飯店→ …

只能先查一步、看結果、再決定下一步，拆解跟執行是交替發生的，不會先把清單列好才開始做。

情境二:全委託給一個常去日本的兄弟

你只丟給兄弟一句話:「幫我規劃三天日本遊，女人會喜歡溫泉跟網美景點」，下次請你吃飯，兄弟收好處辦事開始幫你拆解任務、動用各種資源查資料訂票訂房，過程中還會自我檢討(「我還沒問預算上限,現在查機票可能白查」)，而查桃園機場接駁資訊這種瑣事，兄弟不會親自去查，而是叫剛好在航空公司上班的妹妹協助，自己則專心處理飯店這些需要判斷的大事。

它不只是拆解任務，而是把拆解出來的任務，分派給不同角色去做(兄弟與他妹)。

情境三:自己有規劃的安排

先做一件事(查機票)，查完發現冒出新的待辦(要查接駁交通)，寫進筆記本清單裡，再看清單裡哪件事最急(接駁資訊比訂飯店急)，排到前面優先做，做完再生出新待辦、再排序重複這個動作，直到清單清空。

執行 → 產生新任務 → 重新排序。做一件事記錄後再去排序優先事項。

與情境一不同在於情境一是「憑直覺一路想下去，沒有正式紀錄與清單」，而此情境為「每做完一步，都要正式回頭管理整份待辦清單在進行優先排序」

Subgoal Decomposition 框架

前面舉了三個情境如果理解差異，那恭你已經了解了Subgoal Decomposition的三個框架

  • ReAct
    對應情境一，邊推理邊行動，不預先規劃全部，走一步算一步。

  • AutoGPT
    能自主運作，除了拆解之外還疊加了自我批評、工具整合、任務委派給其他人手這些功能。 這其實就是我們前面學過的上下級協同(Hierarchical Collaboration)的實際案例:
    兄弟 = 中控Agent,負責理解目標、拆解任務、做決策;
    兄弟他妹 = Sub-L1 Agent，只負責被分派下來的簡單任務,不用自己判斷全局。
    只是拆解任務，而是把拆解出來的任務，分派給不同角色去做，跟單純自己邊想邊做的 ReAct 已經是不同層次的設計了。

  • BabyAGI
    執行 → 產生新任務 → 重新排序，單純的任務清單管理迴圈

Chain of Thoughts(推理)

Subgoal Decomposition好之後，針對每一個子任務，Agent 還需要一步步推理，而不是憑感覺直接給答案。這就是 Chain of Thoughts 要解決的問題，而它本身又依複雜度分成四個階段:

IO

直接輸出，無思考過程。例如女友問去哪玩，隨口講一個地方，完全不清過大腦思考的答案

CoT

線性一步步推理。例如女友問去哪玩後，按步驟想先查機票→再查飯店→再排行程。

CoT-SC

多條鏈平行跑完再投票，競爭式協同。例如女友問去哪玩後，自己、阿浩、阿昇各排一套完整行程，並投票選最多人認同的行程。

ToT

邊展開邊評估、可剪枝回溯，Reflection + Self-critics方式。例如女友問去哪玩後，規劃時「沖繩 vs 東京」兩條路線都先想一下，邊想邊評估划不划算，發現沖繩太貴就直接放棄，專心走東京這條線，中途卡關還能回頭換方向。

IO、CoT、CoT-SC、ToT比較

階段 用到的思考機制 行為
IO 無 隨口講一個地方
CoT Chain of Thoughts 線性一步步推理規劃
CoT-SC Chain of Thoughts + 簡易 Self-Critics 競爭式協同，投票選最多人認同的
ToT Chain of Thoughts + Self-Critics + Reflection 規劃時同時納入多個規劃，中途卡關還能回頭換方向

IO/CoT 是「線性思考」，一條路走到底
CoT-SC/ToT 是「多路徑思考」，差別在於 CoT-SC 是走完才比較，ToT 是邊走邊比較、能中途放棄壞路徑。

Reflection(反思)

為甚麼需要有Reflection?沒有他有差嗎?我們一樣以日本之旅講述，如果每次規劃行程犯錯(排太趕惹女友生氣)，你都要花一週
「重新調校自己的旅遊規劃能力」才能學到教訓，那也太沒效率，女友可能受不了生氣氣乾脆不去，這時你需要的是當下就能記住教訓，修正後彙報一版給女友。傳統的強化學習方法，需要大量訓練樣本，還要花很大成本去微調模型權重如:

Agent 這次任務失敗了 → 把這次失敗的資料收集起來 → 重新訓練模型、更新權重 → 才能讓它「學會」不要再犯同樣的錯

但這代表每次想讓 Agent 進步，都要跑一次昂貴、耗時的訓練流程，這是不切實際的，對即時場景來說，太慢也太貴了使用者也不可能接受。

因此才提出一個新框架 Reflexion，不透過更新模型權重來強化語言 Agent。
運用三個 LLM 角色 + 一個記憶模組:

  • Actor:執行動作、產生輸出
  • Evaluator:對 Actor 的輸出打分數
  • Self-Reflection:把評分結果轉換成「文字反思」
  • Memory:把反思文字存起來，成為長期記憶，供下一輪任務參考(這是儲存區，不是模型)

Reflexion 不是真正的學習。模型權重完全沒有改變

Actor 執行 → Evaluator 評分 → Self-Reflection 生成反思文字 → 存入 Memory → 下一輪迭代時,Actor 會讀取這些反思記憶,避免重蹈覆轍

Actor

Actor 是 Reflexion 框架裡負責產生行動、中間推理過程與最終答案的策略(policy)，這個策略由兩部分共同決定:

  • 固定不變的 LLM 權重
  • 會隨嘗試次數累積、不斷變動的記憶內容。

每次呼叫 LLM 時，把記憶內容當作 prompt 的一部分一起輸入，LLM 本身自始至終沒有被改變過。Actor有兩種實作風格:

Chain-of-Thought(CoT)

前面所提純推理，一步步在腦中往下想

想一步 → 做一個動作(查資料)→ 看結果 → 再想

由於此方式只靠訓練時記下的知識進行推理，沒有管道查證或更新資訊，因此容易產生幻覺、講錯過時或冷門資訊。
舉例日本之旅:
憑記憶規劃行程，腦子裡想到哪個景點就寫哪個，沒有打開 Google 查證

為什麼需要外部連結?

LLM 的知識在訓練那一刻就固定住了，遇到這幾種狀況就容易出錯:

  • 訓練資料本來就沒涵蓋到的冷門知識
  • 訓練之後才發生的新資訊(比如最新的營業時間、最新價格)
  • 模型自己記錯、記混了(這就是常聽到的「幻覺 hallucination」)

ReAct

模型推理到一半，可以主動下指令查詢外部環境(搜尋維基百科或Google)，拿到搜尋結果，再繼續往下推理，推理過程中會插入真實查詢動作，不是憑空想。每查一次，都會先寫一段推理(「我查到 A 了，但題目問的是 B,，還需要再查 C」)，讓查詢動作有方向、有目的查完的資訊也才會被真正整合進最後的答案裡。

舉例日本之旅:
邊想邊查這個溫泉飯店現在還有開嗎?直接打開網頁查，查到結果再繼續往下規劃。

補充:ReAct 在前面 Subgoal Decomposition 章節出現過，當時談的是它「邊做邊拆解任務」的特性，這裡則是聚焦在它「怎麼讓 Actor 內部思考」這個面向，兩者談的是同一個框架的不同功能。）

Chain-of-Thought(CoT) 與 ReAct

Chain-of-Thought(CoT) ReAct
運作方式 純推理，一步步在腦中往下想，沒有跟外部環境互動 推理跟行動交錯進行:想一步 → 做一個動作(查資料)→ 看結果 → 再想
適合場景 不需要即時外部資訊、靠內部知識就能推理的任務 需要查證、取得即時資訊的任務(問答、事實查核)
缺點 沒有外部連結，容易產生幻覺、講錯過時或冷門資訊 如果只做行動、沒有推理(純行動基準線)，查了資料也整合不出答案，所以 ReAct 一定要保留推理這一步
論文實測 HotPotQA 上單獨表現略勝 ReAct(29.4 vs 27.4) Fever 上優於 CoT(60.9 vs 56.3)，因為查核任務特別需要即時準確的知識

論文實測資訊

Evaluator

Evaluator 負責針對 Actor 這一次嘗試產生的軌跡打分數，判斷「這次做得好不好、成功了嗎」。輸入是 Actor 執行完留下的完整行動軌跡，輸出是一個獎勵訊號。Evaluator 有好幾種不同的實作算法

1. 精確匹配(Exact Match)

用在像客服或故障排除系統這種有標準答案的問答任務上，直接檢查模型生成的答案，是否跟正確答案完全吻合。這種評分方式最直接、最沒有模糊空間，但也只適用於「答案是固定、可比對」的任務類型。

日本之旅比喻:女友問你這間溫泉飯店一晚多少錢?，答案是固定的、可以直接比對的，你查到的數字要嘛跟官網公告的價格一模一樣，要嘛不一樣，沒有模糊空間，對就是對、錯就是錯。

2. 啟發式規則(Heuristic Rules)

用在像系統架構之類需要跟環境互動、完成一連串動作的商業邏輯或場景權衡。因為這類任務沒有單一「正確答案」可以比對，所以改用預先定義好的規則去檢測特定失敗模式。

日本旅遊比喻:規劃行程沒有「唯一正確的排法」，但可以設幾條啟發式規則去抓明顯的問題

  • 同一天排的景點，交通時間加起來超過 3 小時就標記太趕
  • 訂的飯店距離安排的景點超過 1 小時車程

標記不合理，不用比對標準答案行程表，只要沒踩到這些紅線,就算是合格的規劃。

3. 單元測試(Unit Tests)

用在程式撰寫任務上，直接讓生成的程式碼跑過一組單元測試，通過測試就代表這次輸出是成功的。
日本之旅比喻:排完行程後，拿幾個檢查點去實測驗證通過這些檢查點才算合格。

  • 機票時間跟飯店 check-in 時間對得上嗎?
  • 每天的交通接駁真的銜接得起來嗎?

4. LLM 自評

直接找另一個 LLM 來扮演 Evaluator 角色，讓它閱讀 Actor 的輸出後自己給出評分。這是彈性最高的做法，但也最依賴這個「評審用」LLM 本身的判斷能力夠不夠準確。
日本之旅比喻:行程排好後，找一個有經驗的兄弟通篇看過整份行程，憑他的經驗跟判斷給你打分。

為什麼 Reflexion 只需要「粗略」的訊號就夠?

Evaluator 的要求只有訊號的精細度很低，不代表「設計難度」很低。

傳統強化學習需要設計精細的數值獎勵函數(reward shaping)，像是下棋贏了給 +100，每吃一步棋給 +1，被吃扣 -5，模型依靠這些數值去更新，數字的顆粒度直接影響模型學得好不好。這套獎勵函數往往要花很多心力去調校並不是這麼容易。

而Reflexion 要的只是粗略方向，像是成功/失敗這種二元結果，不需要精細的數值型獎勵。原因是 Reflexion 觸發 Self-Reflection 去做精細判斷的工作，被移到下一棒，Evaluator 不用告訴系統這次做得有多爛、爛在哪，只要告訴系統過不過關就好，為什麼失敗、哪裡出錯、下次怎麼改這些精細的判斷，全部交給 Self-Reflection 處理。所以「粗略」換來的好處，是「不用做強化學習數字的精算」。

日本旅遊比喻:Evaluator 不需要打出這次行程 87 分這種精確分數，只需要一句簡單訊號，「女友這次滿不滿意」二元結果。

但要準確判斷出「滿意還是不滿意」，還是得仔細觀察她全程的表情、有沒有抱怨，判斷這件事本身沒有變簡單，只是不用把「滿意程度」精算成一個分數而已。真正要搞懂「哪裡讓她不滿意、下次怎麼改」，是後面 Self-Reflection 該做的事。

Self-Reflection的天花板，取決於 Evaluator

Evaluator 的品質其實是整個系統的第一道瓶頸，獎勵訊號設計得不好，反思內容自然也會跟著跑偏。「一步錯，步步錯」，或者在計算機科學中常說的「垃圾進，垃圾出」。

這裡舉個例子MBPP(Mostly Basic Python) 問題，最早由 Google Research 提出，用來測試模型能不能根據自然語言描述產生正確 Python 程式，但因MBPP單元測試的情境過低導致輕易就能通過

題目為找出陣列第一個元素

模型自己寫的單元測試:

Evaluator 認為成功，但事實上有學過單元測的朋友都知道這只是Happy Path，但現實中往往更多情境需要考慮，但只要陣列是空的，這段程式碼就會直接拋出 IndexError 而崩潰，這種邊界情況，自產的測試根本沒想到要涵蓋。問題被直接放過，連被檢討的機會都沒有。

Evaluator 判定成功 → 系統認為這一輪任務已經完成，不需要反思 → 疊代直接停止，但這段程式碼實際上還有漏洞，只是沒被自己寫的測試抓出來

日本旅遊比喻:你排的行程只用最順利的情況驗證過一遍(晴天、交通都準時)，沒去想「如果那天下雨怎麼辦」邊界情況。驗證方式太寬鬆行程被誤判成「沒問題」，反而少了一次回頭修正的機會。

還有另一種更隱蔽的風險，如果 Evaluator 正確判定失敗，但打分的依據本身有問題(比如啟發式規則設計得不夠精準)，Self-Reflection 雖然有被觸發，寫出來的反思內容卻是基於錯誤前提推導出來的，等於「做了,但做錯方向」，這種情況比「完全沒被觸發」更難察覺，因為表面上系統看起來確實有在「反思、修正」，只是修正的方向從一開始就偏了。

日本之旅比喻:同一天排超過 3 個景點就算太趕，女友這天確實抱怨了(Evaluator 正確判定失敗)，於是你認真寫下反思:「果然是排了 4 個景點太多，下次每天最多排 3 個」。

但你完全想錯方向了，女友真正不開心的原因，其實是那天一直在轉車，花太多時間耗在交通上，跟景點數量根本沒關係。規則從一開始設計得不夠精準(只看景點數量,沒考慮交通時間)，導致 Self-Reflection 雖然確實被觸發、也認真寫了檢討，但整段反思的前提就是錯的。

這就導致下次規劃，你照著這個「錯誤的教訓」把景點壓到 3 個以內，結果因為完全沒處理交通問題，女友更不開心整趟旅程一直生悶氣，表面上確實有在檢討、有在調整，看起來很認真學習，但方向從第一步就偏了，而且因為每次都有反思紀錄，反而更難發現問題出在「規則本身設錯」，而不是「沒有反思」。

Self-Reflection(反思)

Self-Reflection 拿到 Evaluator 給的分數(通常只是一個數字，或成功/失敗這種二元訊號)，負責把它翻譯成一段有意義的文字說明，當 Evaluator 判定失敗時，Self-Reflection 模型會把這個結果轉換成語言回饋。根據失敗的軌跡跟評估結果，它會生成自然語言反思，診斷哪裡出錯、解釋推理為什麼失敗，並建議下次嘗試該用什麼策略。反思常是具體、很像可執行的指令，而不是空泛的檢討

信用分配問題(Credit Assignment Problem)

產生有用的反思回饋很有挑戰性，因為這需要對「模型到底哪裡做錯」有很好的理解(也就是所謂的信用分配問題)，需要有能力生成一段包含可執行改進建議的摘要。Reflexion 透過對軌跡中「哪些具體行動」導致失敗進行隱式推理，來處理信用分配問題，並為未來的嘗試提出替代策略，沒有額外的演算法去精確定位錯誤步驟，完全靠 LLM 自己讀完整條軌跡後，用推理能力去判斷問題出在哪。

跟傳統強化學習 對照:

傳統 RL(顯式信用分配) Reflexion(隱式信用分配)
怎麼分配信用 用數學公式計算每步的貢獻度 讓 LLM 讀完整條軌跡,自己推理判斷
需要什麼 精心設計的演算法(TD、優勢估計等) 只需要 LLM 本身的推理能力
準確度保證 有數學收斂性質可以分析 沒有正式的準確度保證,完全依賴 LLM 判斷力
成本 訓練複雜、需要大量樣本 不用訓練,一次呼叫 LLM 就能生成

三種產生反思內容的方式

  • 單純的二元環境回饋:只根據成功/失敗這個簡單訊號生成反思
  • 針對常見失敗案例預先定義的啟發式規則:遇到特定已知的失敗模式，套用固定的檢討模板
  • 自我生成:讓 LLM 自己分析失敗原因，不依賴任何預設規則，完全靠推理能力產生反思

這裡跟 Evaluator 的四種評分方式不是同一件事，Evaluator 決定過不過關，反思則是決定檢討報告要根據什麼資訊來寫。

Memory

這裡的Memory是Reflexion 的模組，與Planning同層的Memory是不同的，但他們的概念邏輯很像，兩層:

短期記憶(Short-term / Trajectory) 長期記憶(Episodic Memory)
存的內容 這一次嘗試(trial)過程中的完整行動軌跡 Self-Reflection 產生的文字反思
有效範圍 只在這一輪任務內有效 跨越多輪嘗試持續累積
誰在用 Evaluator 打分數時,讀取的就是這段軌跡 下一輪 Actor 開始執行前,會先讀取這裡

Evaluator 打分數時，輸入的是這次任務產生的完整行動軌跡，這段軌跡本身也被稱作短期記憶，也就是說,短期記憶其實就是 Actor 這一輪跑出來的「工作紀錄」，用完就沒有下一輪的價值，真正會被留下來、影響未來表現的，是長期記憶裡存的反思文字。

對照日本旅遊:

  • 短期記憶是:這次查的機票報價、聯絡過的飯店客服，下次規劃別的旅行用不到
  • 長期記憶則:每天別排超過 3 個景點、訂飯店要考慮跟景點的交通時間，這份備忘錄下次規劃不同的旅行時還翻得到。

Self-Critics(自我批評)

Self-Critics 做的事，是讓 Actor 在產出的當下就有能力自己抓出問題、當場修正，不用等到整個任務跑完、被外部驗證失敗後才回頭補救。如果Actor 生成完一個答案就直接輸出，不會自己回頭檢查，會發生什麼事?

就像寫東西一樣，LLM 不會每次第一次嘗試就寫出最好的版本。差別在於人類會自己重讀一遍草稿，挑出不順、不夠好的地方修一修(對於我在寫文章非常有感觸哈)，但如果 LLM 沒有這個機制，第一版就是最終版沒有人幫它把關，錯字、邏輯漏洞、考慮不周的地方，就這樣直接送出去了。

Self-Critics代表的框架為Self-Refine ，模仿人類修改草稿的方式，讓模型自己生成初稿，再讓模型本身回頭批評自己的初稿，並根據這個批評修正，不斷重複這個過程，逐步把輸出打磨得更好。

對照日本旅遊:排完行程草稿後不急著給女友看，自己先重讀一次寫下問題，再照著這些問題修一版，整個過程都是你自己一個人在做。

Self-Refine 通通是自問自答完成的，同時扮演三個角色:

  • 產生者(Generate):先產生一版初始輸出
  • 批評者(Feedback):把這版輸出送回自己，要求它具體指出哪裡有問題
  • 修正者(Refine):把回饋跟原輸出一起送回模型，請它產出修正版

對照日本旅遊: 想一步 → 挑一個毛病(景點排太多)→ 修一版 → 再挑毛病(忘記溫泉飯店)→ 再修一版 → … → 覺得夠好了，交出去給女友看

現實迭代次數取捨

輪數太少可能還沒改到位，輪數太多反而可能因為沒有標準答案可以對照，讓模型在沒有明確方向的情況下越改越差，同時每多一輪都要重新呼叫模型，成本跟著累加。所以需要「改善空間」跟「成本/風險」之間抓的一個實務平衡點。

對照日本旅遊:改個 2~3 輪左右差不多就夠了，改太多次反而可能越改越亂，原本排得不錯的部分，因為找不到更多毛病硬要挑，反而被改壞了。

小結

Planning 是 AI Agent 從「直接回答」走向「能處理複雜任務」的核心能力。它讓 Agent 可以先拆解任務、規劃步驟、執行後再反思與修正，而不是一次把答案生成完就結束。

這篇的重點可以收斂成三句話：

  • Subgoal Decomposition 讓 Agent 把大任務拆成可以執行的小任務。
  • Reflection / Self-Reflection 讓 Agent 從失敗或不完整的結果中修正策略。
  • Self-Critics / Self-Refine 則讓模型在輸出前先自我檢查，逐步打磨答案品質。

實務上 Planning 不是越複雜越好，而是要在任務難度、迭代成本、輸出品質之間取平衡。簡單任務不一定需要完整規劃流程，但只要任務開始變長、變多步驟、需要中途修正，Planning 就會變成 Agent 能不能穩定完成工作的關鍵。
